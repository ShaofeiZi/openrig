# zrig v0.5.0

> **UI 定位（与 v0.4.7 相同）：** Web UI 处于**维护模式**，仍会发布、仍可运行，但不再增加新功能。**CLI/TUI 是主要产品界面。** v0.5.0 发布 TUI（`zrig` / `zrig tui`），作为新的任务控制中心。

## 摘要 — 终端任务控制 + 上下文库 + Permission Policy + Provider 用量 + 真实 CLI

**终端中的任务控制。** 输入 `zrig` 或 `zrig tui` 即可打开新 TUI：包含文件树 navigator、高密度智能体详情（工作目录、运行时、上下文百分比）、一屏展示整个 fleet 的拓扑 graph、真实的状态/activity 用语、motion design、可用的滚动，以及贯穿界面的真实宽度截断指示。

**v0.5.0 完整包含 v0.4.8 的所有内容。** 两个版本不存在分歧，v0.4.8 的 permission posture 工作和已发布技能均包含在 v0.5.0 中。

Migration 仅叠加。现有 v0.4.8 数据库可通过在新后台服务上运行 `zrig daemon start` 升级。

## 已发布内容

### Permission Policy Built-in 与智能体驱动转换

在 v0.4.8 permission policy 基础上，v0.5.0 发布**内置 policy template，以及将其转换为目标 harness 实时配置的智能体驱动技能**。

- **四个内置 policy template** — `locked`、`standard`、`open`、`yolo`。Package 中的模板只读，可复制后自定义；另提供 `none`，表示有意不使用 policy。
- **`zrig setup --policy <name>`** — 将所选 policy 记录到工作组 spec。参数可以是内置名称（`locked | standard | open | yolo | none`）或自定义 policy 文件路径；自定义 policy 是用户创作的 `.policy.md` 文件。
- **`applying-a-permission-policy` — 用于转换的 bundled skill。** 在工作组 setup/preflight 时，该技能读取 policy spec、检查席位当前 harness 版本、在写入前展示具体 diff，然后将配置写入 Claude `~/.claude/settings.json` 和/或 Codex `config.toml`。绝不盲写。转换有意由智能体驱动，因为 harness permission format 经常跨版本变化，确定性 writer 会在 harness 界面变化时立即失效。
- **两类界面** — **Launch flag** 界面由 zrig 稳定设置，包括 Claude `--permission-mode`、Codex sandbox/bypass、Pi `--approve` / `--no-approve`；这里承载 floor（Claude `acceptEdits`、Codex workspace-write）和 full bypass YOLO 模式。**Config file** 界面（Claude `~/.claude/settings.json`、Codex `config.toml`）承载 allow/ask/deny rule，由技能应用所选 policy。
- **确定性与 best effort 的边界** — launch flag floor 和 YOLO 是确定性的。细粒度 config file rule 采用 best effort，因为 harness rule grammar 会变化；技能会在 diff before write 流程中提示 prefix collision、target first leak、Claude 缺少原生 network gate 等限制。如果转换无法确定，始终可以回退为手工编辑 harness 自身 settings file，或把 YOLO/floor 作为较粗粒度手段。

### Permission Writer 保证由测试固定

v0.5.0 延续 v0.4.8 的承诺：**zrig 绝不会向 Claude `settings.json` 写入 permission entry**，并通过永久 guard test 与 empty writer sweep 固定该保证。唯一允许的例外，是 v0.4.8 自身定义的 project local `acceptEdits` floor。Permission policy discovery 的警告顺序更加清晰：先显示既有 main floor 警告，再显示 policy attachment 警告。此变化只影响呈现，语义边界不变。

### 上下文库

`zrig context` 存储并组合上下文；`zrig walk` 按节奏投递；`--context` / `--body-context` 将已存储上下文以引用方式附加到 `zrig send` / `zrig broadcast` / `zrig queue create`。Grammar 严格：**名词负责存储和组合**，`zrig context` 绝不会自行投递；**动词负责投递**，包括 `zrig send`、`zrig broadcast`、`zrig walk`，或通过 `--context` / `--body-context` 使用的 `zrig queue create`。v0.4.x 的 context window usage viewer 已移除；`zrig context` 名称现在属于上下文库。

### 行为变化（v0.4.8 → v0.5.0）

`rig.yaml` 启动 `context_pack` 条目不再在工作组实例化时投递。**系统会拒绝这些条目，并给出教学式错误，引导使用 `zrig context compose` 与投递命令。** 在 v0.4.8 的短暂窗口内已在 `rig.yaml` 使用 `context_pack` 的用户，应通过 `zrig context compose` 组合 pack，再使用 `zrig send --context`、`zrig broadcast --context`、`zrig walk`，或 `zrig queue create` 上的 `--context` / `--body-context` 进行投递。Bundle router 仍会存储 pack，只是不再在启动时自动投递。

### Provider 用量可观测性

后台服务按主机跟踪账户级用量，用于回答“我是否快达到用量限制”；数据通过 `GET /api/provider/usage` 和 `zrig provider status` 公开。Provider 不报告时显式显示 unknown；多个信号冲突时同时展示双方事实。Codex 账户切换流程保持不变。

### 正确的计划修订

`zrig scope slice approve --re-approve --reason "..."` 会用 append-only audit trail 重新盖戳已锁定计划，取代此前因状态已经 approved 而被迫编辑 `Status` note 的 workaround。

### 真实 CLI 输出

- `zrig ps` 会说明当前仅显示多个工作组中的一个，不再静默限制。
- `zrig send --json` 以 `{fact, consequence, action}` 返回结构化错误。
- Activity hook 修复消除了每次发送都会在整个 fleet 触发的 “producer link stale” advisory，提升运维体验。

### 构建纪律

Contributor gate 与 lane 以 `docs/reference/developing.md` 为唯一真源。

### UI 状态（与 v0.4.7 相同）

Web UI 继续保持 v0.4.7 引入的维护模式：仍会发布、仍可运行，但不再增加新功能。CLI/TUI 是主要界面；v0.5.0 的 TUI（`zrig` / `zrig tui`）是后续任务控制投入的落点。UI 没有弃用，也没有移除；现有部署继续工作。

### Bundled Skill

除 v0.4.8 的技能外，本版本新增两个 bundled skill：

- `applying-a-permission-policy` — permission policy 的智能体驱动转换，详见上文 Permission Policy 章节。
- `delegating-work` — 面向所有席位的工作分配指引。

`openrig-user` 技能已更新为 v0.5.0 上下文库 grammar，包括 `zrig context compose`、`zrig walk`、`--context` / `--body-context`。

## 已知问题

- **Codex `HOME` 修复未进入 v0.5.0** — 一项 permission posture 修复会确保后台服务与 Codex 席位使用相同 `HOME` 环境，使 posture 写入能够到达席位。该修复虽已获准进入 v0.5.0，却被意外遗漏在发布 build 之外，将作为 v0.5.1 的早期 bug fix 发布。在此期间，仍适用 v0.4.8 的部署说明：要使 permission posture 写入到达 Codex 席位，**后台服务的 `HOME` 必须与席位 tmux 的 `HOME` 相同**；任何远程主机升级都必须验证。

## 升级说明

- Migration 仅叠加；在新后台服务上运行 `zrig daemon start`。
- 仍在 `rig.yaml` 中声明启动 `context_pack` 的配置会收到上述教学式拒绝；请迁移到 `zrig context compose` + 投递命令。

## 行为与兼容性

- **Migration** — 仅叠加。
- **`rig.yaml` 启动 `context_pack`** — 实例化时拒绝并显示教学式错误；请迁移到 `zrig context compose` + 投递命令。
- **移除 Context Viewer** — v0.4.x 的 context window usage viewer 已移除；`zrig context` 名称现在属于上下文库。
- **Permission writer 界面** — 永久 guard test 固定以下保证：除获准的 project local `acceptEdits` floor 外，zrig 向 `~/.claude/settings.json` 写入零个 permission entry。
