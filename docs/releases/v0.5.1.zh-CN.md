# zrig v0.5.1

## 摘要 — 产品测试系统，以及通过它发布的可靠性修复

**v0.5.1 为产品提供测试系统。** Scenario 使用与人类相同的命令驱动真实产品，因此产品可以自行证明行为，无需人工逐项检查。本周期的可靠性修复通过测试系统发布，在第一次循环中就证明了它的价值。

**v0.5.1 完整包含 v0.5.0。** 两者属于同一 lineage，没有分歧。

Migration 仅叠加。现有 v0.5.0 数据库可通过在新后台服务上运行 `zrig daemon start` 升级。相较 v0.5.0，没有删除或重命名 CLI 命令/flag。

## 已发布内容

### 测试系统

- **测试用 stub runtime** — scenario 可以驱动的虚假智能体运行时，使其无需真实 Claude 或 Codex 进程即可端到端演练后台服务。
- **Scenario 格式与 runner** — 基于文本的 scenario 格式，以及针对真实产品运行 scenario 的 executor。编写 runner 时发现并修复一个真实问题：过去针对 pane 或 transcript 的文本匹配永远无法匹配两个预期界面，现在可以。
- **Seed scenario** — 三个 seed scenario 针对真实产品端到端运行并全部通过。未能构建的预期 seed scenario 见下文“已知限制”。

### Container Test Bed — 脚手架

本版本发布 container mode 的**脚手架**：argument builder、image identity stamping、runbook 与单元测试套件。**Runner 目前尚不会在 container 中执行**；这些内容会出现在仓库中，但当前没有测试驱动它们。Container mode 执行已安排到后续 scope。

### 通过测试系统发布的可靠性修复

- **真实渲染后台服务 transport failure** — 运维人员会看到实际失败，不再遇到静默 no-op 或泛化错误。
- **Queue persistence** — 两项修复确保 queue record 写入后会反映实际发生的情况。
- **跨机器 send 回归** — 在验证期间发现并修复。这正是测试系统的作用：跨机器证明产品行为，并在发布前捕获回归。

### 小型功能

- **Spec 逐智能体指定模型** — 每个智能体的模型来自自身 spec，而非 fleet wide default，因此不同智能体可运行不同 provider 或 model。
- **随时间跟踪 token 用量** — 后台服务记录 token 使用量，使运维人员可以查看趋势并预测席位何时接近用量限制。
- **消息携带来源机器** — 消息会记录来源机器，使多主机协调清晰可读。

### 其他

- **UI 时序强化** — UI 测试不再因加载时序抖动失败。
- **Queue record 写入后保持真实** — 关闭“已经写入但未持久生效”类问题。
- **未送达消息可见性** — 显示未能到达智能体的消息。该功能落地时发现自 8 月 8 日以来有 9 次真实 handoff 曾被静默丢失。

## 已知限制

- **Container mode 已搭建但尚未驱动。** 仓库中可以看到 seam、argument builder、image stamping、runbook 与单元测试套件，但当前没有测试在 container 中执行。已安排后续 scope。
- **预期 seed scenario 中有三个全绿。** 第十个 scenario 无法构建，因为产品还缺少两项能力：scenario 无法修改运行中系统的 shape；terminal 界面公开的是 navigation state，而非 fleet inventory。这两项能力均已安排后续 scope。

## 行为与兼容性

- **Migration** — 仅叠加。现有 v0.5.0 数据库可通过在新后台服务上运行 `zrig daemon start` 升级。
- **API 界面保留** — 相较 v0.5.0，没有删除或重命名 CLI 命令/flag。
- **v0.5.1 完整包含 v0.5.0** — 同一 lineage，没有分歧。
