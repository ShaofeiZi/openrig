# zrig v0.3.3

## 摘要

zrig v0.3.3 是一次聚焦易用性与真实表达的发布。新增两组顶层 CLI verb（`zrig archive`/`zrig unarchive` 和 `zrig add`/`zrig add-member`）；解决多项长期易用性问题，包括大 payload 启动内容传输、以短横线开头的 `send_text`、cmux 0.64.x 兼容、按名称执行 `zrig down` 以及黄金路径发现。同时收紧三处真实性界面，防止把不明确结果误判为成功：`zrig send --verify` 的投递结果、Codex 恢复门禁和 `zrig whoami` 的 peers 契约。For-You feed 也获得一次“按异常管理”改进，包括下钻终端、decision band 排序和一键批准。Slice 13 的确定性发布界面解析器与技能绑定索引作为产品代码发布，为自动功能发布系统提供支持。

0.3.3 新增一个 migration：`042_rig_archive`（`ALTER TABLE rigs ADD COLUMN archived_at TEXT` 与 `idx_rigs_archived`）。它只追加、非破坏性，不会重构 rigs 行。现有 v0.3.2 数据库会在首次运行 `zrig daemon start` 时升级。

## 本次发布包含的内容

- **大启动文件传输（slice 16）** — 超过 100KB 的 `TmuxAdapter.sendText` payload 现在通过每次调用独立的 tmux buffer（`load-buffer` + `paste-buffer -d -r`）传输，不再塞进单条 `send-keys -l` argv。这样解决了 Linux 上大席位启动包超过 128KB 时因 `MAX_ARG_STRLEN` 导致的静默启动失败。`-r` 保留原始 LF，因此多行 pack 不会在每个换行处提前提交；末尾唯一的 C-m 仍由调用者单独发送。小 payload 继续使用完全相同的内联 `send-keys -l` 命令。成功和 paste error 路径都会清理临时文件与 buffer；每次调用使用唯一名称，因此并行 `zrig up` 席位不会冲突。
- **`send_text` 内联短横线哨兵（slice 17）** — 内联 `tmux send-keys -t <t> -l <text>` 现在带有 `--` 选项结束哨兵，因此内容以 `-` 开头的启动 payload（尤其是席位启动包中常见的 `---` YAML frontmatter）不会被 tmux 解析为 flag。slice 16 的大 payload/buffer 路径本来就不受影响，因为内容经文件而非 argv 传输；该路径保持不变。对于不以短横线开头的内容，此变更没有影响。
- **cmux 0.64.x 兼容（slice 18）** — cmux 0.64.x 重命名了 surface 标识符：`list-panels --json` 行使用 `ref`，不再使用 `id`。Transport 的 `surface.list` normalizer 只映射了 array key，未转换 row key，导致 `surface.sendText` 在新版 cmux 上静默失败。新增 `normalizeSurfaceRow` helper，通过 `ref ?? surface_ref ?? surface_id ?? id` 解析 handle，并且无论 array key 是什么都规范化每一行。同一解析顺序兼容 cmux 0.64.x 和 0.63.x，无需版本协商 shim；适配模式与代码既有的 workspace row 和 create/split handle 处理一致。
- **`zrig archive` 功能（slice 19）** — 新增顶层命令 `zrig archive <rigId>` 与 `zrig unarchive <rigId>`。归档是非破坏性的：保留工作组行、设置 `archived_at` 并发出 `rig.archived` 事件。默认读取排除已归档工作组，避免列表中意外出现；可通过 `zrig ps --include-archived`、`?includeArchived=true` 和 `?archived=only` 重新包含。UI 在 localhost 主机节点下新增惰性可折叠的“归档”区域，由单独的 archived-only query 提供数据。对仅存在于归档中的名称执行 `zrig up <name>` 会被如实拒绝，并提示 `zrig unarchive`；不会静默恢复或继续 fallback。归档运行中/降级工作组时，guard 会显示“事实 / 后果 / 操作”三段式错误，也允许 `--force` 覆盖。UI query invalidation 端到端消费 `rig.archived` / `rig.unarchived`，因此一个窗口中的 CLI 归档会响应式刷新其他已挂载 UI。
- **`zrig add` / `zrig add-member`（slice 24）** — 新增 `add_member` converge op 的顶层命令，可从 YAML/JSON 成员片段文件向运行中工作组的现有 pod 添加成员。它构建于新的 converge spine（`Op` union + differ + `convergeOp`），CLI 只是 converge 界面上的命令式便捷层，并未绕开它。后台服务路由 `POST /api/rigs/:rigId/pods/:podNamespace/members` 将 `AddMemberOutcome` code 映射为 HTTP（404 / 409 / 400 / 201）。MCP 工具 `rig_add` 同步发布。同一 slice 还收紧边缘验证：非数组 `edges` 会被拒绝，不再静默丢弃；edge kind 根据 `rigspec-schema.ts` 导出的规范 `VALID_EDGE_KINDS` 集合验证并复用该集合，避免重复定义，因此 `zrig add` edge 遵循既有 graph 契约。
- **`zrig down` 接受名称或 ID（slice 22）** — 从 v0.2.0 延续的 `zrig down <name>` HTTP 404 限制已消除。Resolver 现在请求 `/api/rigs/summary?includeArchived=true`，先在所有工作组中精确匹配 ID（归档 ID 仍可拆除），再仅在活跃工作组中匹配名称。若活跃与归档工作组同名，会解析到活跃工作组；仅存在于归档中的名称不会按名称解析。随包发布的 `openrig-user` 技能（spec 源码、assets/plugins 副本和 `_canonical` 镜像）以及 `down.ts` resolver 注释均已修正。历史 CHANGELOG 和 v0.3.1/v0.3.2 发布说明保持原样，因为这些版本当时确实存在该 bug。
- **真实的 Codex 恢复门禁（slice 21 FR-2）** — 只有 native-resume-probe 证明席位确实恢复时，`verifyResumeLaunch` 才返回 `ok:true`。尚未解决且需要运维操作的门禁（无法自动关闭的更新、信任、模型选择）以及在有界轮询中始终未达到 `resumed` 的情况，现在返回 `ok:false`、`recovery: attention_required` 和 pane 最后 12 行证据，并通过既有 `HarnessLaunchResult` → startup-orchestrator `startupStatus: attention_required` → `ps`/`status` 投影传递，无需新增状态机制。能够自动关闭的 update gate 仍会正常关闭并继续成功；只有未解决门禁会明确失败。这解决了 herder 在 04.3 干净 VM 上发现的 `kernel_state bootstrap_failed` 失败模式。
- **`zrig send --verify` 真实投递结果（slice 99.0.6.3）** — 以前的 `Verified: no` 混合了两种实质不同的状态：消息已经送达（文本粘贴与 Enter 提交均成功），但发送后 capture 与 TUI 重绘发生竞态；或者消息真的没有送达。谨慎的智能体会在每次发送后额外执行一次 `zrig capture`，不谨慎的智能体则会把 no 当成失败并重复发送。现在响应中明确命名三种结果：
  - `delivered` — 验证成功。
  - `rendered-unconfirmed` — 文本和 Enter 均成功，但 capture 无法再次确认，可能因重绘竞态或 capture 抛错。消息已送达，只是无法确认渲染，并非失败。
  - `failed` — transport 本身失败。
  旧的 `Verified: yes/no` 行为兼容 parser 而逐字保留；新增 `Delivery:` 行携带具名结果，中间状态还会提供 `zrig capture <session>` 确认指引。`--json` 自动透传该字段。
- **`zrig whoami` Peers 契约（slice 99.0.6.1）** — `peers[]` 过去可能被理解为带方向 edge 的子集或主机 inventory，但两者都不正确。现在契约会在响应中明确说明：`peers[]` 是该工作组中排除自身的 roster，由 `rig.nodes` 构建且只跳过自身，不根据 edge/status/binding 过滤；`edges{}` 才是有向 graph；`zrig ps --nodes` 是包含自身与实时状态的 inventory。此次仅增加说明，不改变行为或结构。`WhoamiResult` 新增必填 `peersNote` 字段，包含这三个指针；CLI Peers 标题为兼容已发布测试仍逐字保留 `Peers:` 前缀，并增加指向 `edges` 与 `zrig ps --nodes` 的内联澄清。
- **按名称实例化 Workflow（slice 04.1）** — `zrig workflow instantiate <built-in-name>`（例如 `conveyor`、`basic-loop`）过去会因 `spec_file_missing` 失败，因为 instantiate 将 bare name 直接传给把参数当作文件路径的 `WorkflowSpecCache.readThrough`。只有原始 `sourcePath` 能工作，形成违背新运维人员目标的隐藏路径：发现界面展示了名称，却无法使用。`WorkflowRuntime.instantiate` 现在先按名称在 seeded spec cache 中解析传入标识符，找不到具名 spec 时才回退到 literal sourcePath。Cache 会逐字返回已存储路径，不从源码树重新推导，从而保留生产环境 `dist/builtins` 布局。
- **引导式黄金路径状态澄清（slice 04.2）** — 新运维人员黄金路径此前声称 `zrig workflow list` 会显示 seeded built-in，但该命令实际列出 workflow instance；built-in/spec 发现界面是 `zrig workflow specs`，并用 `(built-in)` 标记。按步骤在 `workflow instantiate <name>` 之前操作的新运维人员会被引向错误命令。现已修正 `docs/reference/getting-started.md` 和 CLI 的 `goldenPathNextSteps()` 第 4 步。
- **For-You 按异常管理（slice 20）** — 仅利用现有信号改进 feed 交互 UX，不改动 0.4.0 attention detection 层：
  - **下钻终端** — 新的 `FeedCardTerminalDrill` 从卡片直接打开解析出的来源/作者会话的终端预览，复用 `TerminalPreviewPopover` 调用 `GET /api/sessions/:sessionName/preview`。表述保持真实：“终端预览”“已捕获快照，并非实时”，绝不声称实时状态。无法解析会话时，下钻入口显示为禁用并给出真实 title，而非打开空终端。
  - **Decision-band 排序** — 稳定的双 band partition 会在既有 newest-first comparator 内，将需要操作和等待批准的卡片提升到 progress / observation / shipped 之前。这不是 ranking engine，不计算分数，也不修改卡片；只在唯一的 Feed merge consumption seam 应用。
  - **一键批准（仅 approve）** — `VerbActions` 新增可叠加的 `oneClickVerbs` prop。APPROVE 点击后直接提交，deny/route 仍需选择并确认。纵深防御包括：prop type 缩窄为 `Extract<MissionControlVerb, "approve">`，误用会产生编译错误；运行时 `ONE_CLICK_SAFE_VERBS` allowlist 会拒绝在调用处通过 cast 强塞的 `"deny"`/`"route"`。它复用相同的 `performSubmit` mutation 路径，因此乐观回执与错误保持行为一致。
- **CLI 发布界面解析器（slice 13.1）** — 使用 TypeScript Compiler API 的确定性 extractor，会在两个 git ref 上遍历 `packages/cli/src/commands/*.ts` 的 Commander 注册，输出结构化发布界面差异，包括新增命令、新增 flag 和删除/重命名界面。支持两种 Commander idiom：链式内联子命令和 factory indirection。输出的是注册名称，因此 `rig-policy.ts` 对外呈现为 `policy`；option name token 只取 `.option()` arg[0]，模板字符串描述不会导致 option 遗漏。每个 ref 通过一次 `git cat-file --batch` 批量读取，快速、离线且确定。失败时输出真实的三段式错误，绝不静默返回空 diff。0.3.3 未将其注册为 `zrig` verb，这是另一项待决策内容；当前 module 作为产品代码发布，并包含 hermetic test fixture 和 v0.3.1..v0.3.2 完整示例。
- **技能 <-> CLI 界面绑定索引（slice 13.2）** — 确定性离线 lookup，将发布界面差异关联到“本次发布影响哪些技能”。它与 slice 13.1 parser 组合且不依赖调用方式。实现已批准的 join grammar：按 component 双向 prefix match，因此 `up` 不会误匹配 `update`；为了保证无假阴性底线，会保守地多包含。绑定索引会丢弃 `--version`，因为规范 grammar 只包含命令路径而非 global flag；技能正文仍以自然语言记录 `rig --version`。随版本发布的 v0.3.2-affected-skills 回归 fixture 来自真实 corpus。

## 面向用户的变更

### `zrig archive` 与 `zrig unarchive`

新增顶层命令。归档是非破坏性的：保留工作组行、设置 `archived_at` 时间戳并发出 `rig.archived` 事件。

```
zrig archive <rigId> [--force] [--json]
zrig unarchive <rigId> [--json]
```

`zrig unarchive` 始终安全，不需要 `--force`，也没有 guard。对运行中或降级工作组执行 `zrig archive` 时会显示“事实 / 后果 / 操作”三段式错误，也可使用 `--force` 覆盖。

默认读取排除已归档工作组：

```
zrig ps [--include-archived]
GET /api/rigs/summary?includeArchived=true
GET /api/rigs/summary?archived=only
GET /api/ps?includeArchived=true
```

`zrig ps` 用 `*` 标记已归档行并显示图例。`--include-archived` flag 会透传到跨主机 argv。

如果 `zrig up <name>` 的名称只对应已归档工作组，系统会如实拒绝并提示 `zrig unarchive`，不会静默恢复或继续 fallback；`--json` 形式发出 `rig_archived`。

UI 在 localhost 主机节点下显示惰性可折叠的“归档”区域。该区域由单独的 archived-only query（`useArchivedRigs`、`?archived=only`）提供数据，而不是在客户端过滤默认列表。`rig.archived` / `rig.unarchived` 事件驱动全局 query invalidation（`["rigs","summary"]` + `["rigs","summary","archived"]` + `["ps"]`），因此 CLI 归档会响应式刷新其他已挂载 UI。

### `zrig add` 与 `zrig add-member`

新增 `add_member` converge op 的顶层命令，从 YAML/JSON 成员片段文件向运行中工作组的现有 pod 添加成员：

```
zrig add <rigId> <podNamespace> <member-fragment-path> \
    [--json] [--rig-root <root>]
```

成员片段可以是 bare member，也可以使用 `{ member }` wrapper。字段名遵循 spec 的 snake_case 结构（`id`、`runtime`、`agent_ref`、`profile`、`cwd` 等）。可选的 pod-local `edges`（`{from, to, kind}` 数组）会完整传递到 converge op：

- 如果存在 `edges` 但它不是数组，则会被**拒绝**，而非静默丢弃：CLI 在 POST 前打印明确错误并以 1 退出；路由返回 400 `validation_failed`；domain 也以纵深防御方式返回 `validation_failed`。
- Edge `kind` 使用 `rigspec-schema.ts` 导出并复用的规范 `VALID_EDGE_KINDS` 集合验证。`kind: nonsense` 返回 400 `validation_failed` 并列出有效集合，不会持久化任何 edge。

后台服务路由：`POST /api/rigs/:rigId/pods/:podNamespace/members`。Outcome 到 HTTP 的映射为：`rig_not_found` / `pod_not_found` → 404；`member_conflict` → 409；`validation_failed` / `preflight_failed` → 400；成功 → 201，正文包含逐节点启动状态。MCP 工具 `rig_add` 同步发布。

### `zrig down` 接受名称或 ID

`zrig down <name>` 现在可以正常工作，从 v0.2.0 延续的 HTTP 404 限制已消除。

```
zrig down <rigId-or-name> [--delete] [--json]
```

Resolver 语义：

- 先请求 `/api/rigs/summary?includeArchived=true`；
- 然后在所有工作组中精确匹配 ID，归档 ID 仍可拆除；
- 最后只在活跃工作组中匹配名称，即 `archivedAt == null`。

活跃和归档工作组同名时解析到活跃工作组，不会产生歧义。仅归档的名称无法按名称解析，请改用 ID，或先执行 `zrig unarchive`。

### Send Text 内联短横线哨兵（slice 17）

内部 tmux `send_text` 路径现在会在用户内容前加入显式 `--` 选项结束哨兵，因此 tmux 不再把以 `-` 或 `--` 开头的内容解析为自身 flag。它是 slice 16 大 payload 传输修复的配套改动：

```
zrig send <session> "content with -- dashes or - hyphens"
```

内容会逐字送达，智能体无需转义或绕开前导短横线，尤其适用于席位启动 payload 中的 `---` YAML frontmatter。这是 `packages/daemon/src/adapters/tmux.ts` 中的后台服务 adapter 修复，`zrig send` CLI 界面本身未变。

### `zrig send --verify` 投递结果

`--verify` 响应现在显式命名结果：

- `delivered` — 验证成功。
- `rendered-unconfirmed` — 文本和 Enter 均成功，但发送后 capture 无法再次确认，原因可能是 TUI 重绘竞态或 capture 抛错。消息已经送达，只是无法再次确认渲染。
- `failed` — transport 本身失败。

旧的 `Verified: yes/no` 行为兼容 parser 而逐字保留；新增 `Delivery:` 行携带具名结果，`rendered-unconfirmed` 时还提供 `zrig capture <session>` 确认指引。`--json` 会透传 `outcome` 字段。

退出码方面，`delivered` 和 `rendered-unconfirmed` 均以 0 退出；中间状态不会被包装成成功或失败。`failed` 以非零退出，HTTP 映射保持不变。工作中 / 等待空闲时的 REFUSAL 有意不携带 outcome，因为没有发送任何内容，拒绝也不是投递失败。

### `zrig whoami --json` Peers 契约

`peers[]` 是该工作组中排除自身的 roster。它不是带方向 edge 的子集，也不是主机 inventory。

- 有向 graph 请读取 `edges{}`。
- 包含自身与实时状态的 inventory 请使用 `zrig ps --nodes`。

`WhoamiResult.peersNote` 在响应内携带该契约。CLI Peers 标题为兼容已发布 parser 仍逐字保留 `Peers:` 前缀，并增加指向 `edges` 和 `zrig ps --nodes` 的澄清。`peers[]` 的名称和结构不变；这只是叠加说明。

### 按名称实例化 Workflow

`zrig workflow instantiate <name>` 现在能端到端解析内置名称：

```
zrig workflow instantiate <name-or-source-path> [--cwd <path>] [--json]
```

内置名称（`conveyor`、`basic-loop` 等）会先按名称在 seeded spec cache 中解析；未匹配名称时，literal source path 仍作为 fallback，二者都不匹配则如实返回 404。这解决了 `zrig workflow specs` 展示名称、但 `zrig workflow instantiate` 无法消费名称的发现/使用分歧。

### 引导式黄金路径发现界面

新运维人员黄金路径现在指向正确的发现 verb：

- `zrig workflow specs` 列出内置/seeded workflow spec，并用 `(built-in)` 标记。在运行 `zrig workflow instantiate <name>` 前应使用此命令发现名称。
- `zrig workflow list` 列出从 spec 创建的 workflow instance；新环境中该列表为空。

该内容已在 `docs/reference/getting-started.md` 和 CLI 的 `setup` 黄金路径文本中修正。

### For-You 按异常管理

仅使用现有信号改进 feed 交互 UX，未改动 0.4.0 attention detection 层：

- **下钻终端预览** — 每张卡片 footer 提供下钻入口，通过 `GET /api/sessions/:sessionName/preview` 打开解析出的来源/作者会话的终端预览。标签为“终端预览”“已捕获快照，并非实时”，绝不声称实时。无法解析会话时会禁用，并显示真实 title。
- **Decision-band 排序** — 需要操作与等待批准的卡片会在既有 newest-first comparator 内提升到 progress / observation / shipped 之前。它是稳定的双 band partition，不是 ranking engine。
- **一键批准** — APPROVE 点击后直接提交；deny 和 route 仍需选择并确认。编译期与运行时 guard 会阻止将一键路径用于非 approve verb（`ONE_CLICK_SAFE_VERBS = {"approve"}`）。

## 运维 / 初始化说明

升级已发布的 CLI 后：

```bash
npm install -g @openrig/cli@0.3.3
zrig --version    # 预期输出 0.3.3
zrig daemon stop
zrig daemon start
```

升级后首次启动后台服务时自动应用 migration `042_rig_archive`。它由 `ALTER TABLE rigs ADD COLUMN archived_at TEXT` 和 `idx_rigs_archived` 组成，只追加且非破坏性，不会重构、重建或删除 rigs 行，现有行不受影响。

新的 `zrig archive` 界面仍由后台服务层默认排除已归档工作组。没有已归档工作组时行为不变。可通过 `zrig ps --include-archived`、`?includeArchived=true` / `?archived=only` query parameter 和 UI 的惰性归档区域重新包含。

新的 `zrig add` 界面要求成员片段文件为 YAML 或 JSON 文档，并使用工作组 spec 的 snake_case 字段名，与 `RigSpec` pod member 的创作格式相同。MCP `rig_add` 工具接受相同片段结构。

对于 `zrig down <name>`，文档中过去要求智能体手动解析工作组 ID 后再调用 `zrig down` 的 workaround 已不再需要；按 ID 调用仍照常工作。
