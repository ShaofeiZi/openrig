# zrig v0.2.0

## 摘要

zrig v0.2.0 是一次重大进展。本版本提供了由后台服务支撑的持久化协调层，包括 stream、queue、project、view、watchdog 监督和 workflow 运行时；同时还带来了重新设计的恢复体验、智能体 starter 注册表、跨主机操作，以及大量生命周期和故障恢复方面的强化修复。这是经历长期内部强化周期后的首个公开版本，因此与 v0.1.12 相比变化幅度很大。

## 本次发布包含的内容

- 新增由后台服务拥有的协调层：`zrig stream`、`zrig queue`、`zrig project`、`zrig view`、`zrig watchdog` 和 `zrig workflow`。
- 新增智能体 starter 注册表，使 RigSpec 成员可以通过 `starter_ref` 引用具名启动预热条目，无需内联这些内容。
- 新增 restore-packet 命令界面，用于跨运行时采集智能体对话包。
- 新增成员级启动来源模式：`session_source: { mode: rebuild }` 和 `session_source: { mode: fork }`。
- 新增跨主机操作：`zrig ps`、`zrig whoami`、`zrig send` 和 `zrig capture` 接受 `--host`，通过 SSH 调用远程 shell。
- 大幅改进 Claude Code 和 Codex 托管会话的生命周期、故障恢复与运行时真实状态。
- 新增 16 个 SQLite migration（021 → 036），为新的协调、view、watchdog 和 workflow 表提供支持；另外还增加了少量可观测性和配置 profile 相关内容。

## 面向用户的变更

### 新的协调命令

新增一组 `zrig` 命令，提供持久化、由后台服务支撑的协调界面：

- `zrig stream` — 发出和查询 stream item，并可通过 SSE 订阅。
- `zrig queue` — 创建、认领、移交和关闭 queue item。包含 `handoff`、`handoff-and-complete`、`update`、`show`、`list`、`whoami`、`inbox-drop`、`inbox-absorb`、`outbox-drop` 和 `outbox-collect`。
- `zrig project` — 将已分类的工作项组织为持久化 project，并提供 classifier 租约、存活检测和回收语义。
- `zrig view` — 查询协调状态的内置及自定义 view，并通过 SSE 消费变更事件。
- `zrig watchdog` — 利用后台服务原生监督能力调度周期性和条件式作业。
- `zrig workflow` — 运行多步骤工作流，保存持久化 trail 记录，并提供 workflow-keepalive 作业。

这些命令会将状态持久化到 zrig 后台服务的 SQLite 数据库中；状态可通过后台服务 API 观察，更新时还会发出 `view.changed` 及相关 SSE 事件。

### 新的 `starter_ref` 成员字段

`zrig up` 现在接受 RigSpec 成员上的 `starter_ref`。启动时，后台服务会从 `agent-starters/` 注册表解析具名条目，并将其内容合并到对应席位按 cwd 划分的指导文件中：Claude 使用 `CLAUDE.md`，Codex 使用 `AGENTS.md`。包含凭据标记的输入会被拒绝，并返回经过脱敏的拒绝 envelope。对同一个成员而言，`starter_ref` 与内联 `session_source` 互斥；对于终端运行时和 fork 组合，plan mode 会预先拒绝 `starter_ref`。

### 新的 `session_source` 模式

成员现在可以声明：

- `session_source: { mode: rebuild }` — 每次 materialize 时，根据具名产物集合重新构建成员。
- `session_source: { mode: fork }` — 启动时，从现有来源 fork 一个新成员。

### Restore-packet 命令界面

新的 `zrig restore-packet` 命令族可以跨运行时采集可恢复的对话包。它包含 Claude 和 Codex 会话记录的解析器与脱敏处理、schema 验证、packet 写入以及 read/validate 流程。此外还新增了 `zrig restore-check` 命令，用于执行恢复就绪检查。

### 跨主机操作

`zrig ps`、`zrig whoami`、`zrig send` 和 `zrig capture` 现在接受 `--host <ssh-host>`，以便在远程机器上运行。CLI 会通过 SSH 调用 shell；调用前无需在远程机器上预先运行长期驻留的智能体或后台服务。

### 生命周期、故障恢复与运行时真实状态改进

- 新增生命周期分类：`recoverable`、`degraded` 和 `attention_required`。Codex 身份验证拒绝现在会在端到端流程中呈现为 `attention_required`。
- 当不存在自动创建的 pre-down 快照时，`zrig up <rigName>` 会回退到手动快照，因此启动流程不再在该路径上静默失败。
- 恢复流程现在有显式 attempt id；运行时真实状态协调可以防止过期状态伪装成存活状态。
- Codex resume 现在通过原生 probe 验证 pane；`zrig expand` 的故障恢复指引会建议先 shrink 再重新 expand，不再尝试启动注定失败的工作组。
- `zrig ps --fields` 现在按照层级 allow-list 拒绝未知 key。`zrig ps` 还支持 `rigName` 别名和有界输出模式。

### 由后台服务启动的智能体现在可以直接运行 `zrig`

此前，由后台服务启动的 Codex 席位需要显式设置 `OPENRIG_HOME`/`OPENRIG_PORT` 环境变量，并要求 PATH 中存在非默认二进制路径。现在，后台服务启动的席位可以直接使用 `zrig`，智能体和运维人员无需为每个席位单独调整环境变量即可使用标准 CLI。兼容入口 `rig` 和 `openrig` 仍予保留。

### Watchdog 帮助、queue actor 推断及其他小型修复

- `zrig watchdog --help` 现在会列出 workflow-keepalive 作业类型。
- 未显式提供 actor 时，`zrig queue` 会从托管会话推断 actor。
- CLI bin 在构建过程中会保留可执行位。
- chatroom wait 测试 fixture 具有稳定时间行为；经过环境清理后，`chatroom wait` 测试不再出现随机失败。

## 运维 / 初始化说明

升级已发布的 CLI 后：

```bash
npm install -g @openrig/cli@0.2.0
zrig --version    # 预期输出 0.2.0
```

需要重启后台服务，才能加载新的 schema 和行为：

```bash
zrig daemon stop
zrig daemon start
```

后台服务首次启动时，会对 SQLite 数据库应用 migration 021-036。按照惯例，migration 只支持向前迁移；如需回滚，请从快照恢复后台服务数据库，将后台服务二进制切回上一个 build，然后再重启。如果希望保留一条干净的回滚路径，请在升级后首次启动后台服务之前创建数据库快照：

```bash
cp ~/.openrig/openrig.sqlite ~/.openrig/openrig.sqlite.pre-v0.2.0.bak
```

如果你维护的是带有运行中工作组的托管控制平面环境，请将后台服务重启安排在升级窗口中。升级过程本身很直接，但停止和启动后台服务会中断活跃的 SSE consumer 以及正在进行的 `zrig up` 流程。

## 已知限制

- 新增的协调界面（`zrig stream`、`zrig queue`、`zrig project`、`zrig view`、`zrig watchdog`、`zrig workflow`）由后台服务支撑。主机上的后台服务必须为 v0.2.0 才能提供这些能力；较旧的后台服务不会暴露这些命令，并且可能静默忽略成员上的 `starter_ref` 等 opt-in 字段。
- `runtime: claude` 不是有效的 RigSpec 运行时写法；Claude 托管席位应使用 `runtime: claude-code`。这是 harness/spec 语法要求，并非产品限制，但曾让运维人员感到意外。
- Watchdog policy 和 workflow spec 持久化在后台服务数据库中。目前还没有用于批量编辑自定义 watchdog policy 的一等 CLI；后续版本会继续改善易用性。
- Phase E 界面（协调层的 rail、rendering 和 steering）有意推迟到后续产品 lane（PL-006/PL-007/PL-008），不属于 v0.2.0。
- 生命周期分类比以前更加真实，但 zrig 仍没有完全显式、达到基础设施级别的状态机。部分故障恢复路径依然依赖启发式判断，而非完美的 provider 原生能力。
