# zrig v0.3.4

## 摘要

zrig v0.3.4 是一次聚焦恢复与韧性的发布。新增两个顶层 CLI verb（`zrig start` 和 `zrig reconcile-session`）；`zrig up` 从默认新建改为默认恢复原会话，并通过 `--fresh <seats...>` 让运维人员显式按席位选择新建；`zrig up` / `zrig restore` / `zrig ps` 的恢复状态界面将所有真实结果归入五个具名状态（`resumed` / `fresh-primed` / `awaiting-decision` / `attention_required` / `failed`）；同时发布周期性快照 scheduler，作为事件驱动快照和拆除快照之下的崩溃保障底线。本版本还解决多项长期恢复问题：通过 `zrig launch` 提供节点粒度的托管部分恢复，使 pod-aware 窄范围启动不再陷入死路；卡在 `attention_required` 的席位现在通过证据门控的 `zrig seat clear-attention` 清理，无需手改 SQLite；Codex profile-v2 preflight 不再把无效 TOML 错分为旧 profile 原因；cmux 启动就绪门禁会真实显示部分工作区状态；缓慢的 Codex resume 也不再被错误分类。

0.3.4 没有新增提升 schema 版本的 migration。现有 v0.3.3 数据库通过在新后台服务上运行 `zrig daemon start` 完成升级。

## 本次发布包含的内容

- **`zrig start`（slice 01）** — 新的顶层恢复入口。一个命令依次执行后台服务启动、等待 kernel 就绪、列出可恢复候选项、通过 picker 或 headless flag 选择，以及逐工作组恢复与 reconcile。它不重新实现底层逻辑，只编排既有原语。Flag 包括 `--last`、`--all`、`--rigs <names...>`、`--json`。候选列表和应用均以 ID 为依据调用 `/api/rigs/:id/up`，同名工作组不会进入按名称调用的 `/api/up` 路由。
- **`zrig up` 默认恢复（slice 02）** — `zrig up <existing-rig>` 现在默认恢复原会话。`--fresh <seats...>` 成为按席位显式选择操作 B（有意 fresh-prime）的方式。此前默认 fresh-prime，智能体必须通过带外知识主动要求 resume。席位结果使用下述五元词汇；当后台服务无法恢复且运维人员未选择 fresh 时，`awaiting-decision` 是真实的零会话状态。
- **`zrig reconcile-session`（slice 03）** — 新的顶层命令。它将已由人工恢复、仍在运行的规范会话重新接入其持久化节点，不会启动、重新启动、终止、重放启动流程、按 resume 菜单、压缩或向 pane 输入内容。它用于解决“我已经手动恢复席位，但后台服务仍显示席位已停止”。节点 ID 不变、不重新生成 key；无法证明的 projection drift 会如实报告，绝不声称对话连续性已获证明。
- **`zrig up --plan` 只读恢复预览（slice 04）** — `zrig up <existing-rig> --plan` 返回按五元词汇描述的只读恢复预览，并提供真实的异步超时。不执行变更；后台服务无法证明可恢复时，不会静默声称可以恢复。
- **恢复状态五元词汇（slice 06）** — `zrig up`、`zrig restore` 和 `zrig ps` 中原先压缩为 2–3 个词的模型，替换为：
  - `resumed` — 已证明原会话连续性。
  - `fresh-primed` — 有意执行 fresh-prime（操作 B），启动了全新会话而非恢复旧会话。
  - `awaiting-decision` — 后台服务无法恢复，且运维人员未选择 fresh；启动了零个会话。这是真实的零会话状态，不是静默失败。
  - `attention_required` — 席位仍在运行或停驻，但需要运维人员操作，例如 auth gate、model selection menu、trust prompt 或卡住的恢复；绝不标为 `failed`。
  - `failed` — 启动 transport 本身失败。
- **Codex Profile-V2 Preflight（slice 07）** — 对带 profile 的启动与恢复界面执行 profile load 检查。旧 profile 检测缩窄为只匹配旧版特有模式：`contains legacy`、`[profiles.<name>]`、`cannot be used while.*legacy`、`legacy profile selector`。此前对 `failed to load configuration` 的泛化匹配也会捕获无效 TOML 的 stderr，并给出错误 migration 提示。现在，无效 TOML 会显示真实解析原因（最多 3 行 stderr）和 TOML 有效性提示。
- **cmux 启动就绪（slice 08）** — 启动路径不再静默生成部分 cmux 工作区。当 cmux 只启动了预期 window / pane 的子集时，席位会真实显示 partial-workspace 状态，并提供一键打开缺失项的入口，不再报告为 launched-clean。
- **周期性快照（slice 09）** — 新增 `snapshots.periodic` 配置族和后台服务侧 `PeriodicSnapshotScheduler`。每个启用的工作组按间隔创建 `auto-periodic` 快照，repository 按 retention keep 进行清理。这提供真正的崩溃保障底线：`auto-periodic` 与 `auto-pre-down` 在同一个恢复 selector 中按新旧竞争，较新者胜出，因此后台服务在拆除快照之间崩溃时，不再丢失任意数量的生命周期状态。`zrig ps` / status 会显示最近快照与保障底线。
- **`zrig seat clear-attention`（slice 10）** — `zrig seat` 新增子命令，以证据门控、运维人员 attest、可审计的方式，将卡住的 `attention_required` 席位 reconcile 回 `ready`。它取代了席位卡住时智能体采用的手改 SQLite / fake clear 方式。审计行记录清理者、来源状态、证据路径和任何运维人员 attestation；`--reason <text>` 是覆盖证据门禁的运维人员 attestation。
- **节点粒度的托管部分恢复（slice 11）** — `zrig launch <rigId> <nodeRef>` 和 `zrig launch <rigId> --seats <a,b>` 通过 orchestration 层按 logical ID 重新启动单个席位或席位子集。它淘汰了 v0.3.x 时代的 `pod_aware_launch_unsupported` 死路以及“改用 zrig up”的 workaround；后者会丢失按席位控制。Held 席位携带 `held-reason`；失败目标显示为 `failed (liveness unknown)`；已经运行的席位只报告状态，不会重新启动。
- **缓慢 Codex Resume 分类修复（slice 13）** — 调整缓慢恢复 Codex 会话的内部分类。过去，确实正在恢复但速度较慢的席位会被 `verifyResumeLaunch` 错误分类；现在会使用同一套五元词汇正确分类。
- **Pod-Aware Claude Resume-Selection Menu（slice 05 rev1）** — 延续 0.3.3 slice 21 FR-2：`ClaudeCodeAdapter.verifyResumeLaunch` 现在像处理 Codex unresolved gate 一样处理 Claude resume selection menu，立即返回 `recovery: attention_required` 和 pane 最后 12 行证据，不发送任何数字选择按键，也不让循环超时后落入泛化失败。

## 面向用户的变更

### `zrig start` — 恢复入口

新增顶层命令。它启动后台服务、等待 kernel、列出可恢复工作组，并通过既有原语应用 restore + reconcile：

```
zrig start                            交互模式：后台服务 + kernel + 选择并恢复
zrig start --last                     Headless：恢复上次运行的所有工作组
zrig start --all                      Headless：恢复所有具有可用快照的工作组
zrig start --rigs <name> [<name>...]  Headless：只恢复具名工作组
zrig start --json                     供智能体使用的 JSON 输出
```

列表和应用均以 ID 为依据调用 `POST /api/rigs/:id/up`。同名工作组作为不同候选项显示；选择结果端到端携带候选项的 `rigId`，因此不会查询按名称调用的 `/api/up` 路由，恢复路径中不会出现 `ambiguous_name` 409。

`zrig start` 只负责编排，不创造新的恢复语义。逐工作组恢复使用与 `zrig up <existing>` 相同的 `/api/rigs/:id/up`；席位结果也使用相同的五元词汇。

### `zrig up` — 默认恢复原会话

`zrig up <existing-rig>` 默认恢复原会话。`--fresh <seats...>` 用于按席位选择有意 fresh-prime（操作 B）：

```
zrig up <existing-rig>                       恢复原会话（默认）
zrig up --existing <name> --fresh dev-impl   仅有意 fresh-prime dev-impl
zrig up <existing-rig> --plan                只读恢复预览（不执行变更）
```

- 成功恢复原会话的席位报告 `resumed`。
- 通过 `--fresh` 选择新建的席位报告 `fresh-primed`。
- 后台服务无法恢复且运维人员未选择 fresh 的席位报告 `awaiting-decision`，即启动了零个会话。Headless 调用者会看到明确提示 `zrig up --existing <source> --fresh <logical-id>`；TTY 调用者会在启动任何 fresh-prime 前，按席位获得 `[y/N]` prompt。
- 仍在运行或停驻、但需要运维操作（auth gate、model selection、trust prompt、卡住的恢复）的席位报告 `attention_required`，绝不会静默重分类为 `failed`。
- 只有 transport 层失败才报告 `failed`。

以前默认 fresh 的行为已经移除。如果工作流依赖隐式 fresh，必须显式指定 `--fresh <seats...>`。

### `zrig up --plan` — 只读恢复预览

```
zrig up <existing-rig> --plan [--json]
```

该命令返回恢复计划而不执行变更：每个节点的预期操作（resume / fresh-prime / awaiting-decision）、计划将使用的快照，以及变更前是否会捕获当前状态。计划路径包含真实的异步超时；无法在时限内完成预览时，响应会明确说明，不会声称计划无误。

### `zrig reconcile-session` — 接入人工恢复的会话

新增顶层命令。在规范 tmux 会话中手动恢复席位后（例如 `claude --resume <id>` / `codex resume <id>`），后台服务仍可能显示席位已停止。Reconcile 会将活跃进程绑定到其自身的持久化节点，并更新投影，使 `zrig ps` / topology / `zrig send` / `zrig capture` / queue routing 恢复工作。它绝不启动、重新启动、终止、重放启动流程、按 resume 菜单、执行 compact 或向 pane 输入内容。

```
zrig reconcile-session <session>                                   自动解析目标节点
zrig reconcile-session <session> --rig <rigId> --node <logicalId>  消除歧义
zrig reconcile-session <session> --no-launch                       显式指定默认模式
zrig reconcile-session <session> --json                            供智能体使用的 JSON 输出
```

`--rig` 与 `--node` 必须一起提供，用于消除歧义。节点 ID 不变、不重新生成 key。Reconcile 无法证明的内容会报告为 projection drift，即未证明元数据字段的列表；对话连续性只作为状态字符串报告，绝不声称已经证明。

### 恢复状态五元词汇

`zrig up`、`zrig restore` 和 `zrig ps` 上的席位级状态字段现在使用以下五个值之一：

| 状态 | 含义 |
| --- | --- |
| `resumed` | native resume probe 已证明原会话连续性。 |
| `fresh-primed` | 运维人员选择有意 fresh-prime（操作 B），启动了全新会话。 |
| `awaiting-decision` | 后台服务无法恢复且运维人员未选择 fresh，启动了零个会话。 |
| `attention_required` | 席位仍在运行或停驻，但需要运维操作，例如认证、模型选择、信任或卡住的恢复。 |
| `failed` | 启动 transport 本身失败。 |

`awaiting-decision` 是新状态，取代过去把零会话结果误报为成功或失败的模式。`attention_required` 覆盖更广泛的“仍在运行但卡住”类别；活跃或停驻的席位绝不会报告为 `failed`。

### `zrig seat clear-attention` — 可审计的卡住席位恢复

这是 `zrig seat` 的子命令，以证据门控、运维人员 attest、可审计的方式，将卡住的 `attention_required` 席位 reconcile 回 `ready`：

```
zrig seat clear-attention <session>
zrig seat clear-attention <session> --reason "<operator attestation>"
zrig seat clear-attention <session> --json
```

- 不提供 `--reason` 时，必须有证据表明席位确实已恢复干净状态，由后台服务侧门禁判断。
- `--reason <text>` 是运维人员 attestation override；审计行逐字记录 attestation 字符串。
- 输出为 `Cleared <session>: <from> -> ready (<clearedBy>)`。审计日志记录 session、from-state、gate 或 attestation，以及运维人员地址。

这取代了手改 SQLite / fake clear 模式。席位的节点 ID 不变。

### 节点粒度的托管部分恢复

`zrig launch` 可以通过 orchestration 层对运行中工作组执行单席位或子集重新启动：

```
zrig launch <rigId> <nodeRef>                单席位（logical ID 或 node ID）
zrig launch <rigId> --seats <a,b,c>          子集（逗号分隔的 logical ID）
zrig launch <rigId> --seats <a,b> --hold-reason "<text>"  非目标席位的 hold 原因
zrig launch <rigId> --seats <a,b> --json
```

- 单目标：`POST /api/rigs/:rigId/nodes/:nodeRef/launch`。
- 子集：`POST /api/rigs/:rigId/nodes/launch-subset`。分别报告 `launched`、带原因的 `held`、`alreadyRunning` 和存活性未知的 `failedTargets`，绝不折叠部分结果。

这淘汰了 `pod_aware_launch_unsupported` 死路和“改用 zrig up”的 workaround。对于运行中工作组的逐席位或逐子集重启，请使用 `zrig launch`；`zrig up <existing>` 仍是整个工作组的恢复入口。

### 周期性快照

这是事件驱动快照和拆除快照之下的崩溃保障底线。新增 `snapshots.periodic` settings family：

| Key | 默认值 | 含义 |
| --- | --- | --- |
| `snapshots.periodic.enabled` | `true` | 总开关 |
| `snapshots.periodic.interval_seconds` | `300` | 每个启用工作组的快照间隔 |
| `snapshots.periodic.retention_keep` | `10` | 每个工作组保留的 `auto-periodic` 数量 |

快照以 `auto-periodic` kind 捕获，repository 按工作组和 `retention_keep` 清理。恢复选择对 `auto-periodic` 与 `auto-pre-down` 一视同仁，二者中较新的快照胜出，因此后台服务在两次拆除快照之间崩溃时，不再丢失任意生命周期状态。`zrig ps` / status 会显示最近快照和保障底线，让运维人员一眼即可确认。

可以通过 settings store（`zrig config set ...`）调整，也可直接使用默认值；scheduler 在后台服务启动时读取配置，并将 `snapshots.periodic.enabled = false` 视为总开关。

### Codex Profile-V2 Preflight

带 profile 的启动与恢复界面现在会真实区分 profile load 失败类型：

- **缩窄旧 profile 检测**：只匹配 `contains legacy`、`[profiles.<name>]`、`cannot be used while.*legacy` 和 `legacy profile selector`。此前对 `failed to load configuration` 的泛化匹配也会捕获无效 TOML 的 stderr。
- **无效 TOML 显示解析原因**：最多显示 3 行 stderr，例如 `expected newline`，并给出 TOML 有效性提示，不再错误地引导迁移 `[profiles.<profile>]`。

Auth refusal 投影路径保持不变；这是 preflight discriminator 中的分类修复。

### cmux 启动就绪

cmux 启动路径不再静默生成部分工作区。当 cmux 只启动了预期 window 或 pane 的子集时，席位会显示真实的 partial-workspace 状态和一键打开缺失项的入口，不再投影为 launched-clean。

### 缓慢 Codex Resume 分类

调整 `verifyResumeLaunch` 对缓慢但确实正在恢复的 Codex 会话的内部分类。过去，缓慢路径会误入 unresolved gate 分支；现在它会使用相同的五元词汇正确分类，并在 readiness probe 确认后达到 `resumed`。

### Pod-Aware Claude Resume-Selection Menu

这是 0.3.3 slice 21 FR-2 的后续改进。`ClaudeCodeAdapter.verifyResumeLaunch` 现在像处理 Codex unresolved gate 一样处理 Claude resume selection menu：无论在内部轮询还是最终 probe 退出路径，都会立即返回 `recovery: attention_required` 和 pane 最后 12 行证据，绝不会发送数字选择按键。

## 应停止使用的旧模式

以下模式已在 0.3.4 中淘汰。请停止使用，并改用列出的支持路径：

- **停止**将 `zrig up <existing-rig>` 当作默认新建。现在默认恢复原会话；需要有意 fresh-prime（操作 B）时使用 `--fresh <seats...>`。
- **停止**将卡住或停驻的席位视为 `failed`。活跃或停驻席位使用 `attention_required`；只有 transport 本身失败才是 `failed`。真实的零会话状态是 `awaiting-decision`，而非 `failed`。
- **停止**在逐席位重新启动时使用 `pod_aware_launch_unsupported` workaround 或“改用 `zrig up`”。请使用 `zrig launch <rigId> <nodeRef>` 或 `zrig launch <rigId> --seats <a,b>`。
- **停止**手改 SQLite 或假清理卡住的 `attention_required` 席位。请使用证据门控的 `zrig seat clear-attention <session>`，或使用运维人员 attest、可审计的 `zrig seat clear-attention <session> --reason "<attestation>"`。
- **停止**只依赖事件驱动或拆除快照保障崩溃安全。周期性快照 scheduler 是底线；可按需调整 `snapshots.periodic.interval_seconds` / `snapshots.periodic.retention_keep`。
- **停止**把无效 TOML 分类为旧 profile 问题。Codex profile-v2 preflight 现在显示真实 TOML 解析原因；只有旧版特有模式才会触发 legacy 检测。
- **停止**通过重新启动整个工作组来恢复人工 resume 的会话。请使用 `zrig reconcile-session <session> --no-launch`：不重新启动、不写入输入、保持同一节点 ID。
- **停止**把部分 cmux 工作区投影为 launched-clean。启动就绪门禁现在会真实显示部分状态，并提供一键打开缺失项的路径。

## 运维 / 初始化说明

升级已发布的 CLI 后：

```bash
npm install -g @openrig/cli@0.3.4
zrig --version    # 预期输出 0.3.4
zrig daemon stop
zrig daemon start
```

0.3.4 没有新增提升 schema 版本的 migration。`snapshots.periodic.*` settings 具有内置默认值（`enabled=true`、`interval_seconds=300`、`retention_keep=10`）；启用崩溃保障底线无需运维人员操作。

从 npm 全新安装 v0.3.4 的运维人员可以立即使用所有新界面。升级现有主机时遵循上述标准后台服务重启流程；0.3.4 host upgrade 流程另行排序，并不是全新安装可用性的前提。

新的 `zrig start` 界面编排既有原语，包括后台服务、kernel 和逐工作组 `/api/rigs/:id/up`。Picker 默认在 TTY 中交互；`--last`、`--all` 和 `--rigs <names...>` headless flag 用于脚本化恢复。

对于 `zrig up` 默认恢复原会话，过去隐式依赖默认 fresh-prime 的任何智能体或脚本，现在必须显式指定 `--fresh <seats...>`。响应使用五元词汇；应将 `awaiting-decision` 视为 headless 环境中“运维人员必须决定”的结果，而非错误。

对于 `zrig seat clear-attention`，席位确实恢复时优先使用证据门控清理。`--reason <text>` override 是可审计的运维人员 attestation 路径；attestation 字符串会逐字写入审计行。

对于周期性快照，高频变化工作组可以调低 `snapshots.periodic.interval_seconds`，需要更长恢复窗口时可以调高 `snapshots.periodic.retention_keep`。默认 5 分钟间隔和保留 10 个快照是一条平衡的底线。

## 已知限制 / 0.3.4 延续项
