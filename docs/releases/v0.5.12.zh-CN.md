# zrig v0.5.12 — 一致的工作、安静的等待与常规 TUI 入口

**状态：** release candidate。Exact cut substance review、最终发布验证和 publication 仍是独立步骤。

zrig 0.5.12 将日常 workflow 操作连接到实用的 progress view、可恢复的 ownership 和可读 TUI。目标是让运维人员或智能体无需维护状态副本，也无需了解私有恢复 recipe，就能开始、理解、调整并回到工作。

## 一次记录判断

经过授权、有 evidence 支撑的 proof judgment 会派生受影响的 proof、slice、任务目标和 project readiness。修正该 judgment 时，会更新其依赖 view，同时保留无关工作和原始 evidence。代码、带 attribution 且 patch equivalent 的工作和非代码产物都能携带真实 provenance。勾选 checkbox、上传文件或关闭 queue item 不会自动成为语义 acceptance；readiness 也不表示已经 publication。

## 了解正在运行哪张 Graph

常规 workflow 检查会区分作者编写的 scope 与绑定的运行中 graph、advisory ordering 与 executable dependency，以及 planning wave 与 runtime step。`zrig workflow revise` 在应用前预览受支持的变更，并保留已完成工作和当前 custody。不兼容 edit 会明确指出需要重新考虑的 decision。Operation identity 与 `zrig workflow operation` 可以恢复结果不明确的 create/revision，而不重复执行 effect。所选 development method guidance 会随 workflow continuation 返回，包括原始 story 和有用的 next action；后台服务不会判断智能体创作正文的含义。

## 为失败指定 Owner 与恢复路径

Exception readiness 会在失败前解释所选 owner，并区分 missing configuration、真实 no match 和 unavailable routing evidence。Routing 使用作者声明的 agent identity，或 registered human fallback。未处理 dependency branch failure 会把 occurrence、owning task 与 wake 一起记录，即使另一 branch 仍然 live。Nudge 失败不会删除 task。修正原因后，使用带 `--occurrence <failed-qitem-id>` 的 `zrig workflow resume` 选择该 failure：过期 exception 会在 redrive transaction 中关闭，同时保留其他 unresolved failure 和已完成工作。

## 安静等待而不丢失工作

健康且未变化的 wait 不会重复发送完整 context packet。针对同一可操作 episode 的重叠 notification 共享 presentation，并保留 provenance。Blocker 变化、delivery miss 和 stranded work 继续保留有界 recovery 或 escalation。常规读取优先显示当前 owner、blocker 和下一项有用 decision，并提供完整 evidence 的显式 expansion。Unknown activity 仍然是 unknown；reminder 不等于 progress。

## 通过同一个 TUI 启动并返回

交互式 bare `zrig` 是常规入口，覆盖首次 setup、后台服务停止时启动，以及重启后返回。TUI 显示 intended instance 与 observed prerequisite，提供后台服务启动，并支持选择要恢复工作的工作组和席位。建议先启动 kernel；未选择工作组保留历史。可用时，resume 会保留所选席位记录的 conversation。Resume 不可用时，系统提供具名 repair，或要求显式确认全新、重新 primed 的 conversation；绝不会静默替换。Launcher 与 native startup 修复会在 runtime 或 dependency 不可用时保留有用错误。

## 在 CONFIG 中浏览通用 Instance Setting

CONFIG 将 instance、workspace/context、display/timezone、waiting、snapshot 和 recovery setting 组织为可读 category，并显示 source 与 override provenance。高级 setting 和完整值仍可发现。Slack 与 human connection 是 CONFIG 的一个 child。打开或刷新 browser 是被动且 secret safe 的；configured value 与 observed application、connectivity、delivery 保持区分。用户无需打开配置文件即可返回常规 scope 和 work view。

## 运维说明

Root、CLI、后台服务与 Web UI package version 为 0.5.12；终端 TUI 保持独立版本 0.1.0。Node 要求和有序 migration head `079_workflow_lifecycle_parallel` 与 0.5.11 相同；本版本未新增数据库 migration。

获得 adoption 授权后，请使用受支持的升级与连续性流程。准备此候选版本不会重启后台服务，也不会更新现有席位。配置检查不是 editor、credential migration、自动 repair，也不承诺每项 setting 都支持 hot reload。仅编辑作者编写的 graph 不会将其采用到已经推进的 workflow 中。Exception repair 不会追溯创建旧代码已 commit 的 failure task；请检查保留的 occurrence，并有意使用受支持恢复 route。

## 验证范围与已知限制

已接受开发结果包含一个较少预先指导、返回/辅助型智能体跨两个依赖 slice 的 journey：记录并修正 proof、修改 graph、等待并返回、恢复一次真实失败 handout check，以及从 CONFIG 导航回工作。定向机制 review 与 installed control 支撑该 journey。Native startup、resume 和 wake observation 保留各自原始 source cut 与时间；这些证据带 attribution 复用，不会被表述成本版本号候选上的新运行。Candidate package 和 generated version check 与这些开发判断分开记录。

- 这不是 unfamiliar human study、无辅助 greenfield usability trial 或全平台验证。Setup 和一次性 native approval 仍属于已记录 journey。
- 最终 exception task 在 placeholder destination 无法接收 nudge 后，通过公开 read/claim/action 消费。它不能证明 native exception delivery 或 external human receipt。
- Quiet wait 测量只证明已测试 workload 的 attention 与 recovery 行为，不是全局 latency 保证，也不证明节省 provider billing token。一项保留的 startup catalog unavailable control 在未变 parent 上同样失败，因此证据不是全绿测试套件声明。
- Whole package substance review、exact release verification 与 publication 仍必须绑定此已准备 candidate。本说明不宣告 npm release 已可用，也不授权 runtime adoption。
