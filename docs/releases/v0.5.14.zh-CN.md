# zrig v0.5.14 — 更清晰的导航、任务目标进度与人类通知

zrig 0.5.14 使打开或刷新时的阅读行为更加可预测，使人类请求与信息更新保持区分，并将 instance setting 和 health 分组到更容易找到的位置。

## 进入并持续阅读

交互式 bare `zrig` 在确认存在运行中工作组后进入常规 TUI。没有运行中工作组的 instance 仍显示 startup chooser。在检测缓慢或 unverified 时，Help、Skip 和 Local 仍保持响应；用户选择其他 route 后，迟到的 observation 不会夺走导航。

页面会区分 initial loading、成功的空结果、refresh 和 failure。Navigator 在 page 与工作组切换期间保持可用。选定页面加载时，先前读取的页面可以带原 scope label 继续显示，但旧内容不包含 action target。同 scope refresh 会保留有用内容、上次读取时间与 Retry。Feed 某个 source 失败时保留自己的数据，而健康 sibling source 继续更新。Confirmed denial、空结果和移除会清除受影响内容；迟到 reply 无法替换当前 selection。首次访问会保留 navigation 和 local feedback。Topology 先提供工作组选择，再读取该工作组，之后才显示无关 fleet detail。Terminal name 在详细 readiness 与 preview 前即可获得。

PROJECTS 会将 malformed mission 与 slice source 显示为本地错误，同时保持健康 neighbor 可读。修正受影响 source 并 refresh 后会恢复内容，且不会在无关工作上方显示 parser fragment。

可选 blocker description 独立加载，因此 description 不可用时不会隐藏主要 queue fact，也不会改变已记录 human recipient。Fleet read 在各阶段共享同一 elapsed request budget；远程 source 失败时保留 local result。重复 proof policy 和 delivery receipt read 会避免重复工作，之后的读取仍能观察当前 input。这些变化减少了测得工作量，但不构成 latency 保证。

Selective restore 和 startup event index 在保留 event history 与 projection result 的同时减少 inventory read 工作。Private query replay 不构成通用 live response time 保证。

Terminal catalog 复用一次 inventory read，不再重复全局 scan。测量结果等价但 query work 更少；这不是通用 latency 保证。既有 saved view discovery、passive preview 和有意 Herdr Open 仍可使用。

## 完成请求并让更新保持安静

Human notification 会区分显式 decision request 与 informational update。Request 携带完整 brief 和 requested action；相关补充 detail 可在 thread 中继续。超过支持上限的内容会被拒绝并要求作者修正，不会静默丢失关键信息。已发布 authoring guidance 要求人类 brief 简洁且完整。

Informational FYI 无需操作或 reply，也不会创建 approval obligation。Delivery completion 与 human decision 相互独立。Partial 或 ambiguous delivery 仍可区分；retry/reply tracking 会保持每个 request 及其 thread 相互独立。未显式声明 intent 的现有 caller 保持 decision 行为。

## 查找请求与 Instance Health

六个顶层入口是 **Topology、Specs、Projects、Terminals、Feed 和 System**。Feed 明确覆盖整个 instance 和所有 human。**Human requests** 显示 recipient 与相关 scope；**Updates** 在既有 outcome 和 health update 之外，还包含已确认 delivered 的 FYI。Delivered FYI 的 delivery obligation 关闭后仍会保留在有界 history 中。读取不等于 approval。Feed 的 Explorer 包含这些 category，条目显示在 content pane 中。Specs kind group 和 Derived terminal view 默认折叠，需显式展开；Saved view 保持突出。Saved membership 仍需有意 setup，打开 terminal view 仍是显式操作。

System 默认打开 instance **Health**，随后是 **Configuration** 和 **Connections**。Contextual Health、global Help 和兼容 direct command 仍可使用，包括 `attention`、`needs`、`feed`、`config` 和 `connections`。

## 理解任务目标进度

在两种终端宽度下，PROJECTS 都会把已完成 outcome、当前工作与 owner、blocker、下一项 dependency 和 slice box 放在 process prose 之前。已接受的 required proof judgment 决定 slice outcome；所有 slice outcome 必须完成后，任务目标才报告 outcome complete。Evidence attachment、quiet activity 和 handoff 本身都不接受 proof。重新打开或已分配的未完成工作保持 open，包括不存在未分配 next slice 时。

实际 custody 与 planned ownership 保持分离。作者定义的 lifecycle 和 publication 与 outcome completion 相互独立；unknown ownership 或 eligibility 保持 unknown。窄屏会保留完整首个 box，其余内容通过滚动查看。

## 运维说明与验证限制

Root、CLI、后台服务和 Web UI 版本为 0.5.14；终端 TUI 保持 0.1.0。Node 要求不变。Migration 081 为 queue record 增加显式 intent 和 supplemental detail。Migration head 现在是 `084_inventory_event_indexes`，新增三个 selective inventory read index；083 新增两个 review read index。Migration 082 为 archived queue transition 增加 nullable identity provenance。Archive 会保留已记录值，并在 archive schema 无法承载这些值时拒绝；legacy unknown value 保持 null。Shared history、RECENT 和 OWNER/receipt reader 现在包含 archived record，因此即使命令或 TUI 代码未变，结果范围也可能扩大。仅执行 migration 不会重建此前丢失的元数据。获得 adoption 授权后，请使用受支持的升级与连续性流程。

Private combined review 在 140×42 和 80×24 下演练 installed journey，包括 entry、refresh、source failure、scope identity、detail/Back、saved terminal Open 和 notification correlation。最初的 Feed source failure 缺陷保留在 evidence 中，修复后又独立复查。Owner candidate native evidence 与 reviewer 针对未变 parent daemon 的 child TUI 是相互独立的 observation。

后续运维检查发现 disruptive navigation 与误导性的任务目标 overview。修正后的 private combined review 覆盖新 navigation、organizer 和 native mission state。错误 NEXT completion finding 被保留、修复，并在两种宽度下独立复查。这些 private result 仍仅适用于已演练 journey 与环境。

9 月 14 日的 VM 检查获接受：加载通常为 0–2 秒，偶尔 timeout；同时检查格式、icon color 和 default view。该观察结果不是通用 latency 或 availability 保证。之后恢复同一 candidate 时保留了 session，但未建立持久 responsiveness 修复。

- 间歇性 read timeout 仍存在。继承的 CLI health check deadline 可能在发送 queue request 前报告后台服务无响应，即使 direct request 实际成功。该缺陷本版本未修复；偶发 server delay 也仍无法归因。
- 较早的 notification 检查使用受控 HTTP response 和 synthetic reply。之后一次真实单 consumer Slack 演练确认完整 decision/detail/FYI posting 与 reply correlation；运维人员确认手机已收到且可读。该观察不能证明 OS push 行为或所有 client。
- Terminal provider evidence 覆盖一次性 Herdr member。此次 review 未证明其他 provider、remote 或 parent host 行为。
- Saved Build watch discovery 已在 VM 中演练，并记录 native judgment。该观察不能证明通用 navigation responsiveness。
- 同时运行的默认 TUI client 仍有既有 programmatic control socket 限制。唯一 test socket 不能证明通用 multi client 隔离。
- Version 与 package check 不会重放开发 journey，也不构成新的 whole source、all platform 或 unfamiliar human usability 结果。
- 已观察的 shutdown drain timeout、已记录 config preservation 不确定性和此前 `recorder_write_failed` observation 均不声称已解决。Recovery evidence 与常规 entry verification 相互独立，不能证明 whole system health。
- 历史 source scan finding 保留各自记录的 disposition；changed path scan 干净不代表 whole source scan 干净。
- Bundled Workflow Spec（包括 `basic-loop`）可能在升级改变 install directory 后从 discovery 中消失，即使 YAML 仍然完整。Discovery 修复明确推迟到 0.5.14 之后；本版本不包含修复。
