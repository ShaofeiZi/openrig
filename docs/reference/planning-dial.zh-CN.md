# 规划档位（planning dial）—— 每件事单独选它的严谨程度

规划是一个光谱，不是非黑即白。当选了 wave 模型后，构建的仔细程度会随 wave 的组成而变化；规划也需要同样的弹性，否则每件事都套用同一套协议——把琐碎的做过头，把困难的做不够。根据工作的不确定性和后果来选档位。

## 各档位 —— 按这件事的性质往上拨

- **P0 —— 迷你需求 + 指引。** 几条可观察的结果和去哪里看；怎么做由构建者自己定。适合简单、可逆、走过很多遍的工作。
- **P1 —— 撰写好的 spec。** 意图、迷你需求、一个先失败测试的证明契约、声明清楚的领地。默认档。
- **P2 —— 再加一轮调研，** 在 spec 冻结**之前**跑，绝不在构建中途跑。调研提示词由一个掌握产品上下文的智能体撰写（见下文门禁）；执行可以扇出给任意智能体——Web 检索腿、文档腿、读代码腿并行。调研以"带引用的上下文"返回，从不返回处方；之后由你结合自己的架构和意图做综合，绿地（设计新东西）和棕地（打磨既有做法）的综合是不同的。
- **P3 —— 再加一轮对抗评审。** 一个没写过这份计划、但掌握产品上下文的人，以产品目标为裁判，从两个方向攻击这份计划。修正以带证明契约牙齿的形式落地——新增或改动一个复选框——绝不写成散文式建议。
- **P4 —— 再加一个盲设计门禁。** 先从零写一份设计，再去读既有先验，然后 diff。相似 → 继续；显著不同 → 停下，和 owner 开一次设计会。

## 上下文门禁

只有装了产品世界上下文的智能体，才能撰写调研提示词、跑对抗评审、或在架构问题上表态。执行侧的调研者和构建者不需要这份上下文——**创建他们指令的那个智能体**必须有。原因：由不知道产品是干什么的人做出来的调研，会流利地回答错误的问题。

## 什么配得上 P2 或 P3 —— 重要性不是判据

当 spec 本会卡在一个未解决的外部未知上时，这件事配得上 **P2**——一个可行性关卡，或一片只有调研能收敛的开放设计空间。当一件事的失败模式对它自己的作者不可见时，它配得上 **P3**：承重基底上，一个看似合理、自洽的计划会把它本要消灭的那个病原样发出来。判别标准是"一个错误的计划会不会代价高、难回退、且从内部看不见"——绝不是"这件事是否核心"。有重要性、但没有不可收敛的未知或作者盲的失败模式，就停在 P1。规划是纯文本工作；让它的范围与未决问题和错误计划的代价成比例，而不是假设每个档位都要固定时长。

## 代价校准

把调研范围限定在可能改变计划的未知上；把对抗评审范围限定在作者可能漏掉的失败模式上。记录解决了哪些问题、由此产生了哪些设计变更，好让 owner 判断所选档位值不值。在构建派发**之前**跑计划好的调研，趁它的答案还能塑造 spec。
