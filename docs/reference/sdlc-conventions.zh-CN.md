# SDLC 约定 —— markdown 控制面

> **真源：** 本仓库文档是 SDLC 约定的活 SSOT。脚手架模板、建议性范围审计、
> `mission-slice-sop` skill 和随包 bootstrap 叠加都指向**这里**——它们绝不能全文复述本文件（复述正是漂移的温床）。

OpenRig 是一座人类从高空掌舵的软件工厂。人记录意图；智能体把意图变成计划、计划变成构建、构建变成证明。TUI 把磁盘上撰写的工作投射出来，并在选定了某个所有证明策略时，从记录的判断派生就绪度。这些撰写约定对智能体是**建议性 / fail-open**：审计记录并建议；选定的证明策略单独管辖谁能裁决。

## 组件菜单 —— 本文是菜单，不是流水线

# PART A —— 简单 SDLC（永远适用）

## A1. 一遍流程

```
intent（这是为什么、完成长什么样）
      → 构建它
      → 亲眼测它
      → 诚实记录你验证了什么、以及你没验证什么
      → 交接（zrig queue handoff）或停下
```

完成时验证整个结果，而不是按增量过一条评审链。极小改动上构建者可以自验这个检查。独立 QA/评审只在项目/任务目标/slice 组合或显式 owner 分派选了时跑；对一个 wave，在它撰写的边界跑。可用角色绝不加门。权威查找在 `product-journey-sdlc.md#resolve-the-selected-path`。带证据来，证明它承诺的用户结果真能用。

对一个发布任务目标，`mission.yaml` 在构建工作开始前还要点名 Git 策略：哪个分支/ref 是累积集成真相、它的 base、以及那个真相何时对账到 main。持续集成到 main、加一条发布线折叠后再一次显式 merge，两种都合法；把选择留隐式不行。

**更重的流程——证明契约、计划锁、C1 drop、证明锁——是 PART B，除非分派，否则不生效。**

## A2. Slice 产物约定（UI 投射什么）

每个 slice 目录带：

- **`SPEC.md`** —— 唯一撰写的节点文件。它的 frontmatter 带 `intent:`，可带 `depends_on:`，是兄弟工作节点 ID 列表；`depends_on` 给兄弟排序，绝不跟随纯路径上下文 trace。正文以三个约定节开篇，按此顺序、用这些确切标题：
  - **`## Intent`** —— 记录的意图，原文。UI 把这段文本投射为 INTENT 节。
  - **`## Mini-requirements`** —— 简洁、一眼看完的需求层（编号列表）。这是人类操作员第一个结构化 catchpoint；批准从这里开始。
  - **`## Proof contract`** —— 承诺交付物的复选框列表（见 §3）。UI 的 DELIVERED 节把每项和它的证据配对。
- **`PROGRESS.md`** —— slice 的验收清单：验收时检查的持久 mission/slice 级 to-do。进行中步骤留在干活智能体自己的 to-do 工具里。
- **`PROOF.md`** —— 保留的证明摘要，显式配对到 `SPEC.md` 证明契约。
- **`proof/`** —— 证明产物目录。策展的规范证据通过 `zrig proof` 带合法 C1 头落在这里（§5）。

旧的 `README.md`、`IMPLEMENTATION-PRD.md` 和前约定树保持无限期可读。新脚手架不创建或镜像它们，修复是增量的：绝不删除、重命名或改写旧字节。

当所属范围选了 `proofPolicy.judges`，用 `zrig proof judge` 在一个契约项上记录一个带署名的 accept/reject/withdraw 决定，用 `zrig proof show` 向上读到 slice、mission 和项目的派生就绪度。最近的 slice、mission 或项目策略选授权评审者；`zrig proof --help` 描述设置、选择器和证据要求。一次修正保留历史和无关判断，不改祖先状态清单。一个产物可以标识非代码工作，而不必伪造提交。证据采集（`proof add`）、策略接受、更高结果判断和发布是分开的。这个可选组件不选 Part B，也不加强制评审门。

三节投射进 UI 的一个评审结构：一个 **INTENT → PLAN → DELIVERED** 垂直栈。缺节的 slice 仍渲染（投射降级为一个暗淡的 "—"，绝不发明内容）——但它在评审里担不起分量。

## A3. 诚实护栏（公共界面 + 带引用的哈希）

### 公共仓库界面要读起来像产品工程

提交信息、代码注释和 markdown/文档是**公共仓库界面**：它们发给那些接触不到、也不关心工作内部如何治理的读者。两条规则，**只进不退**（已有历史不为这些改写）：

- **不逐字引用内部话**，尤其不带情绪或沮丧的。引用一个决定的*技术内容*，绝不引用那个人或做决定时的情绪。
- **不写治理框架。** 写这个改动做什么、为什么它本身正确——不写谁裁决、谁批准、过了哪个内部门。"护栏在锁章时触发，因为否则占位符就会满足 join"是产品工程。"X 在 Y 门裁决了这个"是内部治理漏进公共产物。

测试：项目外的读者应当能在不知道任何内部角色、席位或流程名的情况下，照着这段文字行动。这是同一原则应用到署名和语气上，而不是词汇上。

### 带引用的哈希要说清它覆盖什么

一个作为证据给出的哈希，只有当读者知道它是对哪些字节算的时候才可查。**把覆盖范围和哈希一起说**，两种形式之一：

- **整文件** —— 并说明，包括**尾换行**是否在被哈希字节里；或
- **文件 + 一个确切跨度定义** —— 跨度是*定义的一部分*，不是"去哪看"的提示。

两个诚实的人对同一产物算哈希可能得到不同摘要，谁都没错（例如一个对 frontmatter 块、一个对整文件）。覆盖范围让一个带引用的哈希可验证，而不只是好看。

**用路径 + 锚作为权威，整文件哈希只用于给引用定日期。** 地址在合法内容变化中存活；摘要不存活。

## A4. 当实现发现意图建立在不存在的东西上

一个 slice 的意图只在其假设成立时才可兑现。有时候实现发现一个**锁定的**意图依赖**根本不在**的功能——不是缺个细节，是缺个能力。

**诚实反应是把雄心往下降到现实能撑的程度，并把缺失功能单独立项。** 把 slice 标 **PARTIAL**，写一份文档告诉下游读者准确故事：

1. 意图要求什么（引用锁定文本）
2. 实际发了什么，以及它如何被**按效果**验证
3. **什么没发、确切为什么** —— 点名每个缺失能力，在源头，带证明它缺失的文件和行
4. 这次交付**不**覆盖什么，坦白说——一个夸大覆盖的场景或功能比一个不存在的更糟
5. **按你现在知道的范围排后续 slice**，包括你认为它们该进哪个发布——发现时持有上下文的智能体是这个问题将拥有的最懂读者，下游规划者不该重新发现任何这些

**不可接受的是：** 悄悄收窄主张；悄悄扩 slice 去建缺失能力；或在缩小后的界面上宣布胜利却仍用原 slice 名。**在 slice 内部建缺失件就是范围蔓延。** 发现它们并路由它们，是 slice 正确工作——而一个揭示出真实产品缺口的 slice，产出的东西比它本要交付的功能更有价值。

别过度工程化。整个目标是给下一个读者一个准确故事。

## A5. 弹性中间（比例性——不铸造仪式）

SDLC 恰好三个固定捕获点：**意图** → 一个**成比例的结构化需求** → **证明**。中间一切弹性。对一个小 slice（一个 bug 修复、一份研究笔记），迷你需求**就是**整份规格——约定节必须在好让 slice 投射，但内容随工作伸缩。门是对"从意图到交付的解压不丢信息"的检查，不是文书。脚手架发节；它绝不铸造仪式。

## A6. 审计（建议性、fail-open——永远）

`zrig scope audit`（以及 `zrig workspace validate` / `doctor` 里的建议行）检查这些约定：节标题在场、证明契约形态良好、`proof/` 产物带合法 C1 头、UI slice 引用了 mockup。每个发现**记录并建议——它绝不阻断写路径，也绝不把退出语义变成门**。未知报未知，不报失败。

## A7. 知识住哪（四个指针）

- **本文** —— SSOT。
- **脚手架**：`zrig scope slice create` 为每种模板发 `SPEC.md` + `PROGRESS.md` + `PROOF.md` + `proof/`；`zrig scope mission create` 发一个带意图的 `SPEC.md` + `NOTES.md`。core 只发这个与模式无关的形状；模式插件通过扩展缝加更丰富材料，而不是教 core 一个模式。
- **Skill**：`mission-slice-sop` 教 **Part A**，轻量默认。**Part B** 在下文定义，仅在分派时适用——绝不自选。
- **Bootstrap**：随包智能体叠加在启动时把新席位指向 skill 和本文。

# PART B —— 严格叠加（仅分派时）

> **进入条件：** 下面一切**仅**在人类操作员——或明确转达该决定的编排者——把重路径分派给一个**具名**工作块时适用。如果你不是被分派来的，停下，用 Part A。
>
> **护栏：** 锁**两把，且只有两把**。这里没有任何东西授权对同一份工作再来一轮门、对文档/注释/测试/fixture 设门、或请一个同行对你能亲眼验证的东西设门。**砍轮次，不砍检查。** 当界面变化时，层级**重选**。

## B0. 分派后的一遍流程

```
intent → 迷你需求 + 证明契约 →（UI slice：mockup）
      → 计划锁（zrig scope slice approve --scope spec）
      → 构建锁定集合
      → QA：mockup ↔ 交付物视觉对比
      → 证明 drop（zrig proof add <slice> …）
      → 证明锁（zrig scope slice approve --scope delivery）
```

## B1. 证明契约格式

`## Proof contract` 是一个 markdown 复选框列表；每项是一个承诺交付物，写成一个可观察结果：

```markdown
## Proof contract

- [ ] 合并的 `zrig ps` 默认把所有工作组连同汇总页脚渲染——已捕获。
- [ ] UI：slice 评审标签页渲染三节栈——截图对比锁定 mockup。
```

- 每项（按项文本或 1 基索引）和证明它的证据产物相连——那个配对就是 DELIVERED 节渲染的东西，好让人不必翻几十个产物找哪个证哪个。
- **UI 交付物带一个计划好的 mockup**（`plannedRef`）：规划智能体产出 mockup 并把它附到锁定集合。一个 UI slice 在锁定集合里没 mockup 是不完整的计划。非 UI slice（后端、skills、markdown）没有 mockup、没有 `plannedRef`——那不是缺口，也不是门。
- QA 没真实验证过的交付物在 UI 里显示 `unverified`/`missing`——可见，绝不硬阻断。

## B2. 两把锁（随包动词——不是新机械）

两个刻意的章，都由**同一个**随包动词写（`zrig scope slice approve`，一条 daemon 侧写路径：frontmatter 章 + 只追加审计行一起落）：

- **计划锁：** `zrig scope slice approve <slice> --scope spec` —— "spec 符合我的意图；**这个**产物集合就是要建的。" 把 `SPEC.md`（以及在场的计划 mockup）从文件夹其他一切中钉住。
- **证明锁：** `zrig scope slice approve <slice> --scope delivery`（默认 scope）—— 终态"做完了"签收；触发冻结。

批准是冻结/签收——**绝不**是已证明绿。已证明绿需要一个记录裁决（一个 C1 证明产物，§5）；一个批准章的在场不断言工作已被证明。`--on-behalf-of` 诚实地记录委托（行动者仍是真实调用会话）。

## B3. 证明 drop 与 C1 头（闭集）

证明产物通过随包动词落进 `proof/`：

```bash
zrig proof add <slice> \
  --artifact-type qa \
  --verdict PASS \
  --candidate-sha <被证明的 tip> \
  --money-evidence "一行 money evidence" \
  --file <artifact.md> \
  --evidences "1,3" \
  --media "walk.webm,panel.png" \
  --self-check "我看过捕获；它们显示了主张"
```

C1 头五个必填字段：`slice`、`candidate_sha`、`artifact_type`、`verdict`、`money_evidence`。两个**批准的闭集**（扩展任一个是约定变更，不是本地编辑）：

- `artifact_type`：`guard | qa | rev1-r1 | rev1-r2 | adjudication`
- `verdict`：`CLEAR | BLOCKING | CONCERNING | PASS | NOT-CLEAR`

`candidate_sha` 是 join 键：本产物裁决的被证明候选 tip。`--evidences` 点名这个 drop 覆盖哪个（些）证明契约交付物（项文本或 1 基索引）——那个引用填充计划↔交付配对。`--self-check` 是智能体记录的"我看过证据"断言。`--media` 点名这个 drop 所背书的策展媒体文件（相对 slice 的 `proof/` 目录——同处，绝不绝对）；composer 把它们投射进 DELIVERED 项的证明集。校验在 drop 时发生；审计（§6）兜底走别路到达的产物。**不 drop 而手摆文件进 `proof/` 是反模式**：交付物在 DELIVERED 视图里保持未配对、`unverified`——永远在 drop 上用 `--media` 附媒体。

## B4. 角色契约（什么让结构自强制）

- **规划智能体：** 撰写原文意图、迷你需求和 `## Proof contract`（每个 UI 交付物带它的 mockup `plannedRef`）；产出 mockup；锁计划（`--scope spec`）。
- **构建智能体：** 只对着锁定集合构建；看 mockup，不只看 spec 文本。
- **QA 智能体（拥有对比）：** 对每个交付物——加载锁定的 `plannedRef`，在测试/演示环境产出真实产物，**视觉对比**，通过一次证明 drop 记录裁决 + 备注，并**策展**规范证明集。对超过细枝末节的不匹配：修复后让另一个智能体评审，或带理由踢回——绝不把原始不匹配升级给人。一个没有记录对比的证明 drop 让交付物 `unverified`——可见。

**策展规则：** 主证明集是策展的规范"它现在长这样"证据，智能体为它背书——有界、与交付物 1:1（或少对 1）映射。修复循环的完整产物历史留在 `proof/`，往下钻一层，绝不在主视图。反模式：一堆只追加的东西，人分不清最终和被取代。

## Scratch daemon 密闭性：一个 scratch daemon 打开的 DB 就是你点名的那个

一次 scratch daemon 启动**剥掉继承环境的 `OPENRIG_DB`，并在 scratch `OPENRIG_HOME` 下点名一个显式 scratch DB 路径**——两半，每次启动：

```bash
env -u OPENRIG_DB \
  OPENRIG_HOME="$SCRATCH_HOME" \
  OPENRIG_DB="$SCRATCH_HOME/openrig.sqlite" \
  node <daemon entry> …
```

一个继承的舰队 DB 进到 scratch daemon 是一个**harness 缺陷，无论结局如何**——scratch 上下文读或写了它从不拥有的状态，而有没有东西 visibly 坏了是运气，不是密闭性。

**让这条规则诚实的判别器：** 一个显式 `OPENRIG_DB` 按设计仍赢（`daemon-db-path.ts`）——刻意的 split-path 配置仍然合法、不被碰。本规则管的是**继承进 scratch 上下文**，那里没人做过决定：剥掉你没选的，然后选。
