# 委派工作——这项任务应该由谁完成？

## 核心问题：上下文表现

高质量完成工作，本质上是一个上下文问题。最适合某项任务的智能体，**是已经掌握该任务所需上下文的那一个。**在派生子智能体或自己埋头执行之前，先问清楚谁符合这个条件。

## 决策方式

**问：一个空白执行者需要先读多少材料，才能正确完成这项任务？**

- **需要大量阅读 → 将任务转交给拓扑中已经掌握上下文的真实智能体。**角色结构正是为此存在：长期参与项目的评审者、QA、实现者已经理解工作；无论给空白智能体写多长的说明，也很难比它们做得更好、更安全。
- **只需少量内容——一段提示加少量背景即可 → 派生子智能体。**
- **确实无法确定 → 优先交给真实智能体，或由自己完成。**

## 子智能体使用不足——应更积极使用

对于能够在提示中完整描述的自包含工作，应派生子智能体，避免消耗自己的上下文。例如：追踪、研究、基础信息收集、总结、扫描日志文件、搜索、抓取、网页检索，以及带引用的机械式抽取。这类任务很常见，子智能体却往往没有被充分利用。

## 失败模式——最重要的部分

**子智能体从空白状态开始，你无法预先想到它需要知道的每一件事。**如果任务需要理解大量背景，子智能体就会产生连自己也意识不到的盲点；它仍可能完成任务，却会**返回错误结论**。这不是能力不足，而是它缺少判断“正确”含义所需的上下文。

这就是未知的未知，也是最常见的子智能体失败模式：**缺少上下文的总结比没有总结更糟，因为它看起来像一个完整答案。**在强依赖上下文的工作中过度使用子智能体，会制造比它解决的更多问题；遭遇这种情况的团队可能因此彻底停止使用子智能体，这同样不是正确修正。真正的修复方式不是“避免子智能体”，而是“让任务与其所需上下文相匹配”。

## 实用检验

将任务委派给空白执行者之前，先问：**如果答案看似合理但实际错误，能否被发现？**如果请求方无法用自己已经知道的事实核对结果——例如打开引用、重新执行计数——那么盲点风险不可接受，这项任务应交给持有上下文的智能体。

## 示例

- **适合（→ 子智能体）：**抽取四个应用如何实现某种 UI 机制，要求给出 `file:line` 引用，并明确只报告事实、不提出建议。任务自包含，请求方也能验证引用。
- **不适合盲目委派（→ 交给上下文持有者）：**对重写后的 git 分支重新做独立安全检查。正确完成这项工作，需要知道哪个 commit 范围必须逐字节不变，还要理解真正要寻找的是“轻度混淆的真实值”；这段背景解释起来需要一整段，却只需一句话就可能理解错误。因此，应交给已经持有上下文的智能体。

## 这一规则可以推广

本质上，这条规则是：**将工作交给掌握相关上下文的人**；子智能体适合几乎不需要既有上下文的工作。受众是**所有智能体**——实现席位和 QA 席位与编排者一样，都需要作出这种判断。

## 作出决定之后

- 已决定对 2 项以上独立任务使用子智能体 → 使用 `dispatching-parallel-agents`（负责展开并行执行）。
- 子智能体执行计划中的独立任务 → 使用 `subagent-driven-development`。
- 将任务转交给一个需要由你持续多轮指导的真实智能体 → 使用 `directing-partner-agents`。
- 正确的上下文持有者是人类 → 使用 `human-in-the-loop`。
