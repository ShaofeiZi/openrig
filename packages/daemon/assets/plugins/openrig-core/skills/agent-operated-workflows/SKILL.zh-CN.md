# 智能体操作的工作流

**智能体操作的工作流**是一项控制循环由智能体负责的有边界流程。智能体负责观察、解释、安排有边界行动的顺序、验证效果、适应变化，并在遇到真正的歧义时升级。确定性代码仍然是精确的底层；它不会假装理解存量世界中的所有状态。

## 使用前先明确架构名称

- **AI 增强软件：** 应用代码负责控制循环，并把模型作为一种能力调用。
- **智能体操作的工作流：** 智能体负责一项有明确开始与停止条件的有边界流程。
- **智能体操作的软件：** zrig 智能体或工作组参与某个持续运行应用的实时后端或控制循环。它可以运行多个工作流；参见 `agent-operated-software`。

只调用模型还不够。即使确定性程序会咨询模型，控制循环仍属于该程序。

## 判断智能体是否值得拥有控制循环

当理想路径是确定的，但环境属于存量系统、存在变化、只能部分获知，或穷尽建模的成本高得不成比例时，应使用智能体。此时判断力体现在发现真实状态，并选择下一项安全行动。

如果状态空间封闭，且代码比判断更简单、更可靠，则应优先使用普通代码。解析器、固定数据转换或已完整枚举的状态机，不会因为由智能体驱动就变得更好。

## 明确责任归属

| 负责人 | 职责 |
|---|---|
| Runbook | 负责策略、心智模型、检查点、停止条件和升级规则 |
| 确定性工具 | 负责收集上下文并执行有边界的精确行动 |
| 智能体 | 负责解释、排序、适应和效果验证 |
| 人类 | 负责破坏性歧义和产品策略 |

Runbook 用于指导判断；工具则强制执行不容争议的不变量。

## 执行

1. 确认身份、持久状态、runbook 和承诺结果。
2. 使用无副作用读取或显式 plan 模式检查状态。
3. 根据观察到的状态选择一项有边界行动；不要机械重放理想路径。
4. 在能够证明结果错误的消费者端或状态界面验证效果。
5. 继续前先记录一个可观察检查点，使另一智能体能够恢复。
6. 继续执行、在声明的条件处停止，或携带证据及所需决定发起升级。

被中断或超时的修改属于**结果不确定**，绝不能默认视为失败，也绝不能盲目重试。如果设置兼容期更安全，应把可逆准备工作与破坏性终结操作分开。幂等性是需要按行动逐项证明的主张，不是整个运行过程的标签。

## 构建

提供可组合的动词，而不是乐观的端到端控制器。帮助信息本身不产生行为。读取模式与 plan 模式必须明确。修改应窄小且可以独立读取。失败消息应说明观察到了什么、工具为何停止、什么仍未改变、安全的后续选项是什么，以及证据保存在哪里。保持检查点持久、效果可观察，并让恢复不依赖开发者私有知识。

能力组合是一份可复用配方；这里描述的是推动能力走向结果的执行架构。只有经过实际使用证明后，才能把工作流提升到组合架上。

**公开示例：** 使用 `zrig context get` 加载 `skills/core/openrig-upgrade/SKILL.md`，获取升级 runbook。其相邻的 `scripts/` 目录包含有边界的检查、备份、插件刷新和迁移辅助工具。具体流程遵循该 runbook；此 Skill 保存可复用契约。
