# 学徒交接中的编排者角色

编排者负责判断边界，而不负责继任者的工作，也不负责运维人员的具体按键操作。在具名 owner 作出任何工具都无法推导的那个决定之前，应让现任者继续有效工作、让继任者保持无权限状态，并确保运维操作严格受限。

## 不可降低的底线

- 安装上下文之前，证明身份是全新的且模型与固定版本一致；如果起始历史或模型已经偏离，之后的每一份回执都在描述错误的席位占用者。
- 要求继任者自行推导 layer-5 delta，并由另一人检查，因为阅读 deposit 不等于已经掌握其中内容。
- 在每个边界逐项列明长期职责的保管归属，因为可见的一次性工作通常能顺利交接，而重复性工作最容易丢失。
- 原样保留前任的回访句柄和预先整理的问题，因为没有触发条件的能力不会被使用。
- 通过 `apprentice-successor-seat-cutover.md` 执行运维流程，因为一份可移植 SOP 比会各自漂移的角色本地副本更安全。

## 权限与 gate

**明确表态就是 gate。**在具名 owner 明确表示接受、且效果回执记录该决定之前，继任者可以观察、提问和生成有边界的证据，但不能作为稳定席位采取行动。当继任流程采用 G0–G3 模型时，它们是一套实用的回执词汇；如果风险不值得设置全部四道 gate，也可以明确声明采用更简单的模型。缺失记录必须与主动跳过的 gate 保持可区分。

学徒期是一场对话，不是一轮闯关。选择与错误继任的成本和可逆性相称的证据严格度。绝不能让实验装置本身变成团队文化。

## 转交切换之前

确认 owner 的明确表态、gate 回执或声明的简化模型、完整 deposit、明确职责归属、reserve 处置方式、准确的继任者 token，以及 one-active-walker 所有权。创建一根有明确 owner 的运维接力棒；仅仅知情不等于负责保管。接力棒可以准备并证明切换，但绝不能自动重新绑定。

运维人员报告效果后，从事实源验证 READY：规范席位身份、当前模型、当前 generation、规范 tmux pane、队列清点、职责接受情况，以及实际可用的上下文宽度。全部确认后，才能解除权限冻结。
