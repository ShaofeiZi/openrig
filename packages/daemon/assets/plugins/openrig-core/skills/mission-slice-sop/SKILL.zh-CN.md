# 任务目标/切片 SOP — Part A

使用此 skill 真正**执行** mission/slice 工作：在规范文件中跟踪进展、记录已证明内容、通过这些文件交接，并依靠它们跨越压缩。**请执行这里描述的工作，不要只解释协议。**

**完整约定的单一事实来源：**仓库内为 `docs/reference/sdlc-conventions.md`；安装后为 `$OPENRIG_HOME/reference/sdlc-conventions.md`。此 skill 是简洁的 Part-A 教学界面，不能取代完整约定。

## 先解析工作

运行 `zrig whoami --json`，然后依次解析 `project.yaml -> mission.yaml -> active slice.yaml -> selected component or wave map -> addressed context`。完整查找与优先级规则见 `docs/reference/product-journey-sdlc.md#resolve-the-selected-path`（安装后位于 `$OPENRIG_HOME/reference/product-journey-sdlc.md#resolve-the-selected-path`）。阅读本任务需要的选定地址和源文件；profile 中可用的 skills 是能力，不是强制阅读清单。没有 composition 时，执行轻量 Part A。角色名称和空闲席位不会增加门禁。明确指定的严谨度及人工编写的 wave 边界，继续保留各自的具名检查。

轻量内循环是：掌握当前环境 → 构建 → 亲眼测试 → 迭代 → 记录并返回完整结果。对于小型变更，构建者可以同时负责检查。独立评审只在被选中时运行；在人工编写的 wave 边界上运行一次，而不是每个切片一次。

Part B 定义在约定的单一事实来源中，只有明确分配给具名工作时才运行。如果你认为有必要，应向所有者说明原因，并继续沿选定路径推进，直到选择发生变化。

## 适度原则——此 SOP 为交付服务，本身不是工作

可工作的产品才是交付物。这些记录只用于让工作经受住交接、压缩和评审，除此之外别无目的。**让流程与风险匹配。**`zrig scope audit` 后盾是**建议性、失败开放**的：它永远不会阻止构建，也不是开始工作前必须通过的门禁。如果你在约定文件或审计上花费的时间超过正在运行的产品，请停下来构建产品。对小型改动运行全套流程是拘泥字面，不是勤勉。

## 三种角色契约

- **规划智能体：**用切片自身的语言记录其用途和“完成”的含义；UI 交付物应产出 mockup，供构建者查看（没有 mockup 的 UI 切片说明计划不完整；非 UI 切片不需要 mockup——这不是门禁）。
- **构建智能体：**完成构建，并**查看 mockup**；通过实际运行验证。
- **QA 智能体（负责比较）：**逐项交付物比较计划与实际结果，记录结论和说明。如果不一致：修复后重新评审，或说明原因并退回——绝不要把原始不一致直接升级给人类。

这三者是分工，不是一串门禁。小型切片可由同一智能体同时承担三种角色。

## 当前文件契约

> 这些文件是**工作的操作界面**——你在其中跟踪和记录，通过它们交接，也依靠它们跨越压缩。保持其最新，工作才能持续。但它们为产品服务，不是产品本身。如果你在润色文件而实际内容仍未交付，就是本末倒置：先去构建，再回来更新文件。

- **切片：**`SPEC.md`、`PROGRESS.md`、`PROOF.md` 和 `proof/`。
- **任务目标：**`SPEC.md` 和 `NOTES.md`。

## 各文件规则——何人 / 何时 / 如何

### SPEC.md
- **何人：**规划所有者负责编写；构建者和评审者将其作为范围与意图来源。
- **何时：**创建时，以及工作范围发生变化时。
- **如何：**切片 frontmatter 中包含 `intent:`，并以 `## Intent`、`## Mini-requirements`、`## Proof contract` 开篇。任务目标在同一人工编写节点文件中承载意图和任务目标级规格。内容深度应与工作相称。

### PROGRESS.md
- **何人：**编排者负责 `§1`（当前状态）；每个智能体记录自己的结果。
- **何时：**交付状态发生实质变化时，以及验收时。
- **如何：**每项结果一行（复选框），向下链接详情；确保 frontmatter 的 `stage`/`verified` 如实。

### PROOF.md + proof/
- **何人：**处理此切片的 impl/QA 搭档。
- **何时：**在宣布切片完成之前。
- **如何：**说明验证了什么、如何验证——必须通过**实际效果**：运行它并查看结果。支持性媒体放在 `proof/` 下。如实说明已证明和**未证明**的内容；诚实地说“这一半未经测试”，比打勾更有价值。如果切片提供写入动词，应优先使用它，不要手工放置文件，这样制品才能携带自身来源信息。

### NOTES.md
- **何人：**任何智能体都可更新 `§1`（当前最重要内容）；每个席位拥有并追加自己的 `§A–§X`。
- **何时：**任务目标上下文发生实质变化时；准备压缩的智能体必须**在压缩前将状态写入此处，并在恢复时读取**。
- **如何：**累积团队知识——`§1` ≤ 5–15 行（门禁、待决事项、意外情况）；逐席位记录后续工作（最新内容为准，其他席位只读）。优先使用指针，不要重复内容。

## 生命周期（4 个阶段）

**SCAFFOLD**（`zrig scope` 从模板创建文件）→ **POPULATE**（智能体随工作推进填充文件）→ **PROJECT**（Living Notes UI 将其读取为 INTENT → PLAN → DELIVERED）→ **VERIFY**（`zrig scope audit`，建议性）。“自由格式写入 + 确定性验证。”

## 热土豆（交接）

每轮结束都要把工作交出去——使用 `zrig queue handoff` 交给下一个智能体。handoff 动词是**事务性的**：它会同时关闭源 qitem 并创建由 `--to` 所有的新 qitem，因此工作棒不会丢失。交接只能终止于编排者席位，因为只有它掌握判断是否应暂存工作的上下文。

**普通 `zrig queue create` 行只是信息**——是一条持久消息。它不是工作棒，也不承担这一义务。传递真实工作时使用 `handoff`；只提供信息时使用 `create`。

持有工作棒时绝不要进入空闲状态。

## 验证（确定性后盾）

切片关闭时运行 `zrig scope audit`。所有约定检查都是**建议性 / 失败开放**的——只记录并提出建议，绝不阻止写入。修复真实问题，跳过不适用项，继续推进。**无需获得干净的审计分数才能继续。**

## 阅读终端捕获——已知陷阱：幽灵自动补全文本不是真实内容

使用 `zrig capture` 捕获 pane 时，灰色 / 幽灵自动补全建议**不是真实内容**——它们只是自动补全预览，不是已输入、已暂存或已提交内容。**这经常误导智能体**：有人把同伴输入框中的幽灵建议当成“即将发送的暂存文本”，随后基于一段从未真实存在的字符串推理。

**规则：**完全忽略幽灵/自动建议文本。只有 pane 中**已提交/已渲染**的输出是真实内容。重要时应在来源处（git、队列、实际事件）验证，绝不要依据捕获画面中的幽灵行。

## 关键时刻检查清单

- **正在开始切片？**→ 你是否知道它的用途和完成标准？UI 切片是否附有 mockup？**你是否位于轻量路径上？**（除非任务目标所有者分配了覆盖流程，否则答案是“是”。）
- **正在完成切片？**→ `PROOF.md` 是否记录了通过效果实际验证的内容，包括未覆盖部分？`PROGRESS.md` 是否更新？任务目标 `NOTES.md` 是否刷新？是否通过 `zrig queue handoff` 完成交接？
- **准备压缩？**→ 将状态写入任务目标 `NOTES.md`；恢复时读取它及活动切片的 `SPEC.md`、`PROGRESS.md`、`PROOF.md`。
- **开始任务目标？**→ 阅读任务目标 `SPEC.md`、`NOTES.md` 和约定的单一事实来源。
