# 智能体运营的软件

**智能体运营的软件（Agent-Operated Software）**是指持续运行的应用程序，其在线运行时的后端或控制循环中包含 zrig 智能体或工作组。应用界面可以非常轻量：结构化状态和专业角色承担实际工作，UI 则让这些工作便于理解和干预。

## 从统一分类开始

- **AI-enabled software：**应用程序代码拥有控制循环，并将模型作为其中一项能力来调用。
- **Agent-Operated Workflow：**智能体负责一个有明确开始和停止条件的有限过程；参见 `agent-operated-workflows`。
- **Agent-Operated Software：**智能体参与持续运行应用程序的实际运行时。

一个应用程序可以组合多个 Agent-Operated Workflow。仅有一个有限工作流，并不会自动使其外围产品成为 Agent-Operated Software；同样，单次模型调用也不属于这两类，除非有智能体负责控制循环的一部分。

## 智能体是后端的一部分

在这种架构中，行为并不只存在于函数里，而是分布在智能体、skill、指令、bootstrap 文件、schema、Markdown、YAML、JSON、目录和确定性工具之间。因此，异常结果既可能来自代码缺陷，也可能来自控制平面的连贯性缺口。决定修复哪个层级之前，应先追踪真正产生该行为的完整路径。

这并不意味着可以容忍 zrig 核心或其他坚固基础层中的缺陷。遇到这些缺陷时，应复现问题、修复代码并执行完整质量门禁。优先修复连贯性的快速策略，只适用于可恢复的智能体运营应用层；这类层的状态和行为能够以较低成本检查和修复。

## Markdown 是控制平面

Markdown 对智能体足够有用，同时也保持了人类可读、可干预的特性。应把意图、工作状态、证据和决策写入拥有稳定地址的产物，而不是留在私人聊天或不透明的自定义数据库中。schema 和约定必须与实际运行行为保持一致，因为智能体群体会把这些文件当作可执行上下文来行动。

采用**渐进式披露**。skill 的名称和描述是热触发器，正文则是冷过程。描述负责说明何时加载，而不是如何工作；正文应将读者引向准确的事实源，避免复制内容并形成另一套分叉规范。

脚本也可以充当提示。优秀的脚本会返回智能体需要的上下文或准确效果；如果无法完成，它的失败信息应说明观察到了什么、为何停止，以及有哪些安全的后续动作。确定性机制放在工具中，需要判断的部分交给智能体。

## 让产物能够自证完整性

工具生成产物时，不要让每个消费者各自发明一套完整性检查：

1. 先写入临时路径，绝不直接写最终路径。
2. 验证真正可能出错的属性，例如时长、流、分辨率或 schema。
3. 刷新数据并以原子方式将临时产物重命名为最终路径。
4. 写入 manifest，最后再写 `.done` 哨兵文件。

消费者应依据共享证明采取失败关闭策略。文件名或退出码不能替代内容验证。

## 使用智能体 SDLC 构建

根据目标和项目策略选择所需的严格程度。工作范围关系、具备归属和证据支撑的条目判断，以及真正独立的更高层判断，应由不同责任方负责。单个条目判断会推导其上游就绪状态；智能体不应同步父级复选框、队列标签或状态描述。完成采集不等于获得接受，就绪也不会自动发布或推进工作流。请使用 `openrig-operating-model` 和 `zrig proof --help` 了解受支持的判断、纠正和读取路径，并确保历史锁与证据始终可寻址。人类负责提供干预、品味，以及项目授权明确保留给人的决策。

对于 studio 应用程序，正在运行的产品通常是最好的迭代界面。只有当独立 mockup 能解决运行中应用无法以同等低成本暴露的真实设计不确定性时，它才值得制作。省去的是重复产物，而不是视觉评审或证明契约。

## 修复最窄的权威层

找到所有受影响智能体实际消费的生成器或事实源。代码缺陷在代码中修复，缺失的触发条件在 skill 中修复，格式错误的契约在 schema 中修复；随后通过真实消费者验证。编辑渲染产物或安装副本只会产生临时分叉，并不是真正的修复。

这种收益会不断累积：对共享应用控制平面的修正，会改变下一个智能体的起点。持续运行的智能体运营系统正是以这种方式改进，而不必让某个人类永久充当请求路由器。
