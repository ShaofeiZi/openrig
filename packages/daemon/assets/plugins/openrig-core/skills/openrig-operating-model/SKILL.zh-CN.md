# OpenRig 运行模型

**标准术语：运行模型（Operating Model）。**它描述 OpenRig 拓扑如何组织每一种上下文，
让任何智能体——无论是冷启动、全新启动，还是已经历五代交接——都能找到所需内容，并知道
应把新学到的知识写在哪里。人工编写的上下文保存在可寻址的 Markdown 与 manifest 中。
受支持的写入器负责记录语义判断；对应的读取模型始终可以从这些制品重新构建。

本技能负责定义整体结构：树、链、追溯方式，以及人工知识的放置位置。解析已安装上下文时，
应使用当前库地址和项目选定的 loadout；私有语料库不是必需的公开依赖。

本技能目录中的配套实现资源：

- `templates/` 与 `scripts/`——起始模板和工作工具，详见 §8。

## 1. 一口气理解整个模型

所有内容都位于**两棵树**之一，而每种上下文都是一条**链**：同一个文件名出现在树的每一层。
要了解某件事，就要**从当前位置向根节点追溯**，在每一层读取那个同名文件——较近层级会细化
或覆盖较远层级。**追溯（trace）**（§5）就是使用你自己的文件读取，有意识地完成这次向上遍历。

- **拓扑树**——工作如何完成：`fleet → instance → rig → pod → seat`。
- **工作树**——产品如何构建：`project → mission → slice → proof item`。

一个 **instance** 是一个 OpenRig daemon 及其管理的 rigs；一个 **fleet** 是全部 instances。
daemon 在哪里运行属于部署事实，不是层级；当你指某个特定实例时，请说出该 instance 的名称。

**单父级法则：**追溯只沿目录路径进行，除此之外什么都不看——不读取指针字段、不跟随链接、
不产生分支，永远如此。追溯是迷失的智能体用来重新定位的工具，因此它必须比所纠正的任何问题
都简单：只沿路径向上时，失败只会以明显方式出现。若子项还与第二个父级有关，请添加
`also-serves:` **注解**（供人类和智能体阅读，但任何遍历器都不会沿它行走）；真正的双父级关系
通常意味着该项应上移一层，放到共同祖先下，再用提及向下指向具体位置。运行中的多对多关系
存在于队列标签中，并随实际使用维护。旧版 `serves:` 行只为扁平布局提供过渡桥梁：从不要求、
从不遍历，并会随着工作正确嵌套而删除。

**文件名法则：**每条链只使用一个名称，而且每一层完全相同。文件夹告诉你它属于**谁**；
文件名告诉你它属于**哪类内容**。两个不同 rig 中都名为 `pm-lead` 的席位，各自拥有不同的
`LEARNED.md`——路径就是身份。绝不要为不同层级发明不同名称（例如 SEAT.md、RIG.md）；
那会同时破坏追溯、自我描述以及所有工具。

## 2. 网格——每个层级存放什么，由谁维护其真实性

下表就是模型本身。如果只记住一件事，请记住这张表。

### 拓扑树

这些链承载某个**位置**的真实情况。某一**类**事物如何运作——即运行模型——由不绑定模式的
`openrig-core` 插件提供；运行模式插件（`openrig-lab`、`openrig-factory` 或 `openrig-hq`）
可以进一步细化它。

| 层级 | `CULTURE.md`——价值观 | `LEARNED.md`——当前这个节点学到的内容 | 真实性维护者 |
|---|---|---|---|
| fleet | 默认文化（随 OpenRig 发行） | fleet 级实践经验 | **operator agent** |
| instance | *（继承）* | 此 daemon 上所有 rig 都成立的经验 | **该 instance 的 operator** |
| rig | 该 rig 的章程 | 此 rig 的实践经验 | **该 rig 的 orchestrator** |
| pod | *（继承）* | 此 pod 的实践经验——即**上下文域**：对该 pod 中任何人有用的内容 | **该 pod 的 lead** |
| seat | *（继承）* | 此 seat 的实践知识——**真正修复交接问题的文件** | **该 seat 自身** |

**链文件位于节点上，而不位于承载节点的架子上。**`rigs/`、`pods/`、`seats/`、
`missions/` 和 `slices/` 都只是架子——追溯会经过它们，但不会期待那里存在链文件。

### 工作树

**只有一个人工编写的节点文件：`SPEC.md`。**意图位于它的 FRONTMATTER 中；规范位于正文中。
旁边还有四类职责和写入者都不同的文件或目录：

| 文件 | 含义 | 写入者 |
|---|---|---|
| `SPEC.md` | 节点本身——`intent:` 可组合，正文描述规范 | 节点所有者 |
| `NOTES.md` | **实践记录**——用执行者自己的话记录实际发生了什么 | 任何正在执行该工作的人 |
| `PROOF.md` | 证明交付物符合原始意图的证据 | prover |
| `PROGRESS.md` | 人工叙述与历史 checklist 标记；当前证明就绪度从带归属的判断派生 | 范围所有者与 provers |
| `proof/judgments/` | 由 `zrig proof judge` 写入并保留的逐项判断回执 | 所属证明策略选定的 judges |

**scaffold 可以创建 `NOTES.md` 及其起始说明，但其中的实践条目绝不会被生成或投影。**
它是工作树中的实践文件，正如 `LEARNED.md` 是拓扑树中的实践文件——它是现场笔记所在的层级，
原始观察在有资格进入节点本身之前先放在这里。实践文件不参与渲染路径，正因如此，人们可以
放心地自由书写。

**旧版名称：**较旧的工作区可能使用 `MISSION_NOTES.md`。旧内容应继续可以寻址；链上请使用
`NOTES.md`，因为这个名称适用于每个层级。

| 层级 | `SPEC.md`——frontmatter `intent:`（为什么）+ 正文（必须构建什么） | 进度 | 真实性维护者 |
|---|---|---|---|
| project | 只有 `intent:`——稳定，仅在真正转向时改变 | 派生汇总 | 项目的 PM |
| mission | `intent:` 与成比例的 mission 级规范；组织 slices | 派生的子项就绪度；独立的结果判断 | mission 的 PM |
| slice | `intent:` 与具体 slice 规范 | 派生的证明就绪度 | slice 所有者 |
| proof item | proof contract 中人工写下的承诺 | 针对该修订、由证据支持且带归属的判断 | 选定的 judge |

**当前验收模型：**范围关系与策略写在 manifest 中；每项判断只针对其承诺、证据及策略修订记录
一次。slice、mission 与 project 的就绪度逐级向上派生。不同的结果判断或发布决策仍拥有各自的
权威。队列所有权和通用 `done` 只是保管事实，并不等于证明已验收。历史 checkbox 标记保持
可读，但不会因此获得当前事项的权威。

使用 `zrig proof --help` 查看受支持的读写路径。项目所有者在 `project.yaml`、
`mission.yaml` 或 `slice.yaml` 中选择 `proofPolicy.judges`（距离最近者优先），并使用精确的
actor 地址。不存在隐式的固定角色评审传送带。
`zrig proof judge mission/slices/slice#1 --verdict accept --reason 'Observed the outcome' --evidence proof/result.md`
会解析事项身份、修订、证据摘要和重试身份。证据既可以是现有旧版制品，也可以是非代码结果。
与补丁等价的受审对象还应通过 `--comparison` 指明其实际比较/采纳回执；该判断由智能体负责。
`zrig proof show` 返回当前依据与保留的回执；它不会发布任何内容。

若要纠正，请使用 `reject`；若先前的接受结论已不再成立，则使用 `withdraw`。历史记录保留在
对应的 proof 归属位置。重复请求返回原始回执和当前就绪度；`--replace` 用于在纠正后有意重申
一条旧的、内容相同的判断。承诺、策略或证据发生变化时，都需要当前判断。可选的显式
`<!-- proof-item: stable-id -->` 标记可在措辞修改时保留身份；否则产品会从完整承诺派生身份，
并报告歧义。

**意图可以组合，正文不能。**追溯在每个层级读取 `intent:` **字段**，因此四个层级会展开成
四句话，而不是四份文档。只有当你正站在某个节点上时，才读取它的正文。

    compose.py up <node> --name SPEC.md --field intent --root <project>

某一层级的文件存在却缺少 `intent:` 时，应报告为缺口——mission 没有意图本身就是重要信息，
绝不能静默跳过。

**旧版 `README.md` 节点永久保持有效**——解析器优先选择 `SPEC.md`，并在缺失时回退，
因此不会强迫任何内容迁移，休眠中的 missions 也无需处理。

**PROGRESS 保持独立。**叙述和旧版标记作为证词予以保留。对于已选择 proof policy 的 project，
当前就绪度来自 `zrig proof show` 和现有共享视图，而不是手工维护的父级 checkbox 或复制的状态
文字。`scripts/compose.py progress` 仍是旧版 checklist 渲染器；它不证明带归属的验收已经发生。
意图向下组合，证明就绪度向上聚合。

**这些列背后的轴：**每种上下文都有一个*模板*侧（发行内容——SOP、默认文化）和一个*经验*侧
（实际运行中学到的内容——LEARNED、文化修订）。两者只有变化速度不同：价值观像章程一样很少
且有意识地变化；实践像工作笔记一样持续且低成本地变化；意图只在真正转向时变化。保持每个
文件应有的变化节奏；不要把笔记上升成章程，也不要在章程上随意涂写。

## 3. 为什么需要这个模型（它修复的失败）

席位知识需要一个继任者和其他运行时都能读取的持久归属位置。仅依赖某个运行时的私有记忆，
或只发一个紧急交接数据包，都可能遗漏长期职责和实践背后的原因。通用运行技艺应放在共享技能中，
特定位置的知识应放在该席位的 `LEARNED.md` 链中。交接时，将当前链与交接数据包一起读取；
在声明就绪前，补记任何缺失的工作上下文。每一任占用者维护该席位学到的内容，交接数据包只承载
当前这次转换。

## 4. LEARNED.md——实践文件（所有层级；以 seat 为例）

章节按以下顺序排列——参见 `templates/LEARNED.md`：

1. **Header**——坐标、它细化的 SOP、更新时间（来自时钟命令，绝不依赖记忆）。
2. **MY JOB HERE**——此 instance 的实际职责，以直白的操作语言描述。
3. **STANDING DUTIES**——每项周期性职责，以及各自的节奏和发生位置。写在其他地方的职责会在
   下次交接时消失；本节正是它们得以保留的原因。
4. **HOW I WORK**——工作中学到的实践，**每一项都附带理由**。当世界发生变化时，带有原因的
   实践可以重新判断；脱离理由的规则会比理由存活得更久，最终被错误应用。
5. **GATES & AUTHORITIES**——此 instance 可以独立决定什么、绝不能擅自假设什么。权威要么有
   书面依据，要么根本不存在。
6. **KEY RELATIONSHIPS**——它向谁交接、由谁评审、向谁汇报。
7. **TRIGGER POINTERS**——“当 X 发生时，读取 Y。”把指针附着到需要它的*时刻*；启动时阅读
   清单会逐渐失效。
8. **LESSONS**——带日期，最新在前。定期将旧条目提炼进 HOW I WORK，或删除它们。

**大小只是软性指引，不是规则。**文件应尽可能精简，但必须如实覆盖工作所需——注意力就是预算，
每个读取者都要支付。有些席位确实需要更多内容；应按工作需要书写。需要警惕的失败模式是只增不减
的规则手册。在沉淀边界（清除或交接前）将经验提炼为带原因的实践；依靠这个习惯，而不是行数限制。

## 5. 追溯——有意识地重新定位

追溯就是**用你自己的文件读取**沿链行走，并写下自己所处的位置：我正在做什么
（queue/NOTES）→ 遵循什么契约（SPEC）→ 朝向什么意图（`SPEC.md` 的 intent 字段，从叶到根）
→ 采用什么实践（LEARNED + SOP）→ 处于什么价值观之中（CULTURE）。最后写下几行结论。
`scripts/compose.py up` 可以为你组装任意链。

两条规则赋予追溯价值：

- **你的读取才是追溯。**凭记忆写出的追溯只是背诵——如果没有打开文件，就没有完成追溯；
  你只会自信地重新推导自己已有的漂移。
- **报告断链，绝不要服从断链。**文件缺失、日期过期、意图与可观察现实矛盾——应报告给负责
  该层级的所有者。这正是链保持真实的方式：它们通过实际使用接受审计。链只为决策提供信息；
  它本身绝不强制任何行为——过期地图不能阻止真实工作。

**何时追溯——只有一个原则：***当变化已经足以让你对自身位置的理解可能过期时，就执行追溯*。
例如：完成一大段工作后；处于边界时（启动、交接、新 mission、感到困惑）；或有人要求你重新定位时。
为什么不简单规定“每 N 小时一次”：重复的定时提示会逐渐被智能体忽略，空闲席位还会积累仪式化追溯，
挤占真实上下文。如果日程安排仍适合你的场景，可以使用；但更应优先根据变化证据决定是否执行
*动作*：`scripts/trace-due.sh` 会确定性判断“自上次追溯后是否发生了足够多的变化？”，答案为否时
保持静默，因此调度器可以任意频率调用它。

## 5b. 追溯与 `zrig walk`——一个概念，两种方向

两者因为共用一个词而容易混淆。它们并不冲突；它们是从两端观察到的同一件事，值得牢记其中关系。

**链是按顺序排列、应逐项吸收的上下文序列。**存在两类链，两者都符合这个定义：

- **层级链**——树的每一层使用同一文件名，并向上读取（`LEARNED.md`；带 `intent:` 的
  `SPEC.md`）。序列依据的是*位置*：叶 → 根。
- **启动链**——席位启动时的阅读序列。序列依据的是*入门顺序*。

**链可以用两种方式遍历，唯一真正的差异如下：**

| 方向 | 驱动者 | 机制 | 时机 |
|---|---|---|---|
| **PULL** | 智能体 | `compose.py up` 渲染链；智能体读取它 | 智能体已唤醒且具备足够定位能力，可以主动查找——追溯或重新聚焦 |
| **PUSH** | orchestrator | `zrig walk --through <files> --pace <n>` 将内容逐项发送到窗格 | 智能体*无法*自行启动——刚清除、重新预热或冷启动时 |

**两个方向都依赖节奏控制，这也是关键机制。**每项之间的吸收过程才能让链真正被理解；即使字节
完全相同，一次性拼接倾倒也属于交付失败。因此 `zrig walk` 会在各项之间等待 `--pace`，而组合后的
渲染内容也应作为序列逐项阅读，不能当作文本墙略读。

请用不同名称表示两个方向：

- **TRACE**——拉取式向上追溯。`compose.py up` 将节点到根的链渲染出来。
- **`zrig walk`**——将内容按节奏推送到席位窗格的动词。

当前追溯工作流使用 `refocusing`。交付回执与智能体的阅读深度报告回答不同问题；只有节奏控制
并不能证明已经理解。

## 6. 写入——两项原则

1. **你的 LEARNED.md 属于你。**在完成工作的过程中，当你学到如何执行该工作的新知识时，
   应用自己的话把它写入文件，再继续前进。若其他人希望修改它（纠正或新原则），他们应告诉你，
   再由*你*写入——别人直接写进你文件的知识从未真正属于你。唯一例外是：当 instance 为空或
   损坏时，其负责人写入必要内容，将这些行标记为“为该 instance 编写”，下一任占用者再用自己的话
   重写。
2. **发行内容属于其作者。**`openrig-core` 的 operating-model 技能和发行文化只能通过各自所有者
   修改，不能由某个 instance 原地编辑。如果它对所有人都不正确，应向其所有者提出变更；如果它只对
   *你*不正确，则应写入 LEARNED.md。

无论写在哪里，都要记录日期（从时钟获取）；纠正历史时添加带日期的修正，不要静默改写历史。

## 7. 组合视图

任何节点都可以被**渲染**：把它的链组装成一份文档（`scripts/compose.py`；`up` 表示从叶节点看到的
有效视图，`down` 表示某个根节点下的所有链文件——在树根运行 `down`，即可用一份文档看到完整运行
图景）。遵循三条规则：

- **渲染文档由工具生成，绝不编辑。**链文件才是真相来源；渲染只是它们的快照视图。
- **每次链渲染都以 TRACE 开头**——这是渲染时派生、从不存入任何文件的树形定位标题：每层一行，
  展示其状态（已植入 ✓ / 未植入 ⟂ / 过期标记 ⚠ / 缺失 ✗），并在叶节点标出“你在这里”。
  它像 `tree` 展示目录形状一样，在你读取任何正文前先展示上下文形状：你位于哪里、哪里正在告警。
- **当批准必须冻结精确内容时**（例如规范的 plan-lock），应记录*渲染结果的哈希*——冻结字节保存在
  批准记录中，链文件则保持可供读取和修订的活跃状态。

高层级席位无需读取全部内容，也能通过**根渲染 + diff** 维护对变化中 fleet 的当前心智模型：
渲染树根，与上次渲染结果比较，只读取差异（`scripts/trunk-diff.sh`）。

## 8. 知识应该放在哪里——放置规则

**上下文应放在需要它的最窄范围内；只有没有范围归属的内容才属于技能。**席位专属知识 → 该席位的
LEARNED.md。Rig 实践 → 该 rig 的文件。只有真正与范围无关的技艺（对任何地方的任何智能体都有用）
才属于技能层。

### 决定“文件还是插件”的唯一轴：类别或位置

- **链保存关于某个位置的知识**——*这个* seat、*这个* mission。它在结构上**不可共享**，因为路径
  就是身份。
- **插件保存关于某个类别的知识**——某类 seat 的职责、某领域的技艺、某种运行模型。它可共享、
  可版本化，也可跨 harness 使用。

**插件不能保存 LEARNED。**插件是共享的；LEARNED 属于具体 instance。两个 rig 安装同一个
orchestrator 插件时，不应共享其中一个席位对自身合并工作台的经验。因此，链与插件并存，而不是被
插件取代。

**插件也是分发机制，这带来一项硬性测试。**插件会发行技能，技能可能附带脚本；**该脚本必须无需
修改即可在陌生人的机器上运行。**因此它通过配置解析路径（`zrig config get workspace.root`），
绝不依赖字面路径，也绝不要求智能体自行判断多个候选目录中哪一个才是真实目录。如果用户把工作区
指向 Git 仓库或 `projects/` 文件夹，一切都应无需额外设置而继续工作。**只能在作者机器上运行的
脚本，无论多么正确，都不具备可发行性。**

### 什么内容属于节点内部——写入一句话前先做两项测试

**节点保存对此位置成立且持续成立的内容。**

- **可移植性。**如果一句话放到陌生人的机器上仍然成立，它就是关于某个类别的知识，应放在本技能
  或插件中，而不是树上。完全可移植的节点正文，就是误入链中的文档。
- **易变性。**如果某个值的变化速度快于文件编辑速度——例如 SHA、数量、状态、成员名单——文件中
  应保存**用于推导该值的命令**，而不是答案本身。

**然后判断应放在哪棵树。**陷阱、实践和工作方式属于*拓扑*树上的位置知识（`LEARNED.md`）。
正在构建的内容属于*工作*树（`SPEC.md`）。同一个 rig 同时拥有两棵树，但两者仍不能混杂。

**规范深度应与层级成比例。**project 承载稳定意图；mission 在同一份人工编写的 `SPEC.md` 中承载
其意图与 mission 级规范。Slices 给出具体实现范围。遵循选定的 `mission-slice-sop` 和任何显式
mode overlay；mission 规范并不要求重复每个 slice 的全部细节。

### 另一条轴：受众不等于成熟度

两者相互独立。把它们合并很诱人，因为合并后的形式看起来更整齐。

- **受众决定知识放在哪里**——哪个层级、哪个文件。某项内容属于 pod 层，是因为该 pod 中任何人
  都能从中受益，仅此而已。
- **成熟度是文件中某一行的属性**——认知阶梯：数据 → 观察 → 现场笔记 → 洞见 → **canon**。
  这套词汇已作为 `stage:` 枚举发行（`wip | provisional | established | canonical | superseded | retired`）。

pod 级事项可以只是原始观察；seat 级事项也可以是 canon。**技能可以包含尚不成熟的内容，同时仍是
正确归属位置**，因为文件位置由受众决定。

**因此，晋升为 canon 并不意味着沿树上移。**这是成熟度事件，可以发生在任何层级——若 seat 级
观察具有普适性，它可以直接进入技能。成熟度来自证据：反复出现、独立佐证、可测量成本、经受变化、
经受证伪尝试。**关于机制的事实可以跳过阶梯**（*反引号会在双引号 shell 字符串中执行替换*，
用一条命令即可验证）；**关于实践的推断必须逐步积累**（*绝不要向大型 rig 广播*来自一次事故）。

**LEARNED.md 不是一个分阶段事项——它是承载所有内容的基础。**它的梯度取决于位置：底部带日期的
追加日志是原始观察，顶部精炼章节是经受住考验的内容。将提炼动作绑定到**触发点**：在沉淀边界
（清除前、交接前）进行提炼，此时本来就要求写入，而且作者仍记得每一行存在的原因；重新聚焦只负责
*发现*日志已经长过提炼部分。

## 9. 建立结构

`scripts/scaffold.sh` 使用 `templates/` 创建所有缺失的链文件，并且**绝不覆盖或删除任何内容**——
因此，全新工作区与运行中的系统可以使用同一条命令，只是起始状态不同。创建的文件会标记为
UNSEEDED，直到其真实所有者写入第一个真实版本。**绝不要为其他 instances 批量生成 LEARNED.md
内容**——让每个 instance 编写自己的首个版本，既能让知识真正形成，也能暴露哪些席位尚无法描述
自身工作。

## 10. 常见陷阱（仅列出上文尚未说明的内容）

- 编辑渲染文档，而不是其链文件——你的编辑会在下次渲染时静默丢失。
- 通过跟随指针、解析 serves 或添加分支来“改进”追溯——追溯的全部价值就在于只沿路径向上，
  不会以隐蔽方式失败；请保持追溯只依赖路径。
- 为另一个智能体总结本模型，而不是直接把它指向这里——摘要会成为另一份可能偏离来源的副本。
- `scripts/` 中的脚本有些带有 macOS 特征（`stat -f`）；在其他操作系统上信任它们之前，
  请先验证平台兼容性。
