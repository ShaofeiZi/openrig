# factory-rsi——单工作组 RSI 工厂 MVP

此工作组**就是**一个递归自我改进循环。一个工作流（`factory-rsi`）推动一个切片经过内部循环：**规划 → 实现 → 检查 → 审查 → 发布**。dogfood 与这条门禁循环解耦：它在带外持续使用**已发布**产品，并将发现反馈给**下一轮**规划周期。这条反馈边正是整个设计的意义，而且不需要人类参与循环。

## 循环如何运行

- **内部循环由引擎路由**，而不是编排者。检查或审查失败会路由回构建阶段，进行有边界的修复；干净的审查结果则进入发布准备。没有人手工在循环中传递工作包。
- **Dogfood 位于带外。** 它持续针对已发布产品运行——不是对发布前构建产物执行第二次 QA——并记录会成为下一轮规划输入的发现。RSI 递归保持无门禁：dogfood 发现无需人类门禁即可进入下一轮规划（人类**可以**通过 roadmap 调整方向，但绝非必需；MVP 中没有 loop-stop）。
- **发现是已记录状态，不是记忆。** 下一轮规划基于已记录的 dogfood 发现构建，绝不依赖某个席位的聊天历史。
- **异常先交给编排者**（WF-5 档位）；人类只在更高层知情。触发 `max_hops` 属于异常；一次恢复只授予一个额外的有界窗口——循环绝不会失控。
- **发布是人类行为。** 发布席位负责准备说明、文档和 PR，并在人工门禁处保留发布决定权。任何席位都不得 push、打 tag 或发布。

## 席位

| 席位 | 运行时 | 职责 |
|---|---|---|
| `plan-planner` | claude-code | 将语料库和此前发现转化为一个可构建的切片规格 |
| `build-implementer` | claude-code | 构建切片并产出证明 |
| `check-qa` | codex | 检查产物；检查失败时循环回构建阶段 |
| `review-reviewer` | codex | 执行审查（使用与构建者不同的运行时） |
| `dogfood-tester` | codex | 在带外持续**使用**已发布产品；记录发现并反馈给下一轮规划 |
| `release-manager` | claude-code | 准备发布并保留人工门禁 |
| `orch-lead` | claude-code | 异常档位的目标——只处理异常 |

席位继承各自运行时的默认模型（不按席位固定模型）：规划、构建、发布和编排使用 claude-code；检查、审查和 dogfood 使用 codex，从而相对于构建者获得跨运行时多样性。

## 部署

作为随产品交付的启动器，此工作组与工作区无关——对循环应改进的任意真实仓库运行 `zrig up factory-rsi --cwd <repo>`；规划者的产品意图语料就是该仓库中的真实规格。
