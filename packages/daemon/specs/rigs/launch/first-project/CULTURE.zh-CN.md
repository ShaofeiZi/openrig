# 第一个项目

在启动时选定的仓库中工作。用户提供期望结果；所有者负责让它完成实现、适当检查并形成持久结果。更改任何内容前，先阅读仓库说明及已有的 project/mission/slice 上下文。如果没有选定工作流，应保持路径轻量。不要为了第一个任务安装一整套发布流程。

## 接收工作

运行 `zrig whoami --json` 并检查 `zrig queue list --owned --limit 1000`。开始工作前先认领已分配的行。对于模糊请求，先检查相关代码，再只询问那个会改变结果的关键决定。用户从终端消息发起工作时，应在实现前从自己的席位创建并认领持久任务；未绑定的用户 shell 无需伪造队列身份。

第一次进行有实际意义的代码修改时，请 dev-check 对确切 diff 及其承诺行为进行独立检查。后续检查应与工作后果相匹配。通过 `zrig queue handoff` 交接，并提供仓库路径、候选 commit 或 diff、已运行检查以及任何限制。当前语法请查阅 `--help`。不要把聊天文本当作工作记录。

检查者针对该候选版本记录观察结果，并将可执行的问题返回给所有者。所有者负责解决问题，并在队列中记录最终结果与后续安排。证据应指向项目现有工作制品；如果项目尚无工作树，则指向仓库内的任务说明。不要因为另一行已关闭，就把当前变更标为已接受。

## 边界与后续工作

本地编辑和 commit 必须限制在已分配变更内。发布、推送、release 和破坏性操作都需要单独授权。权限提示意味着工作尚未完成；应明确指出缺少的确切决定，并保留该行。

重新进入时，应读取当前队列状态和项目制品；不要重复已完成的变更，也不要启动重复席位。使用用户可以亲自操作验证的方式解释结果，说明未检查的内容，并指出下一项有价值的行动。让项目在同一所有者地址上保持随时可接收下一目标的状态。
