# 系统化调试

## 概述

随机尝试修复会浪费时间并制造新 bug。快速补丁会掩盖底层问题。

**核心原则：在尝试修复前，始终先找到根因。只修症状就是失败。**

**违反此流程的文字要求，也就是违反调试精神。**

## 铁律

```
未调查根因，不得修复
```

如果还没有完成阶段 1，就不能提出修复方案。

## 何时使用

适用于**任何**技术问题：

- 测试失败。
- 生产环境 bug。
- 意外行为。
- 性能问题。
- 构建失败。
- 集成问题。

**以下情形尤其要使用：**

- 面临时间压力（紧急情况最容易诱使人猜测）。
- “只做一个快速修复”看起来显而易见。
- 已经尝试过多种修复。
- 上一次修复没有奏效。
- 尚未完全理解问题。

**以下情形也不要跳过：**

- 问题看起来很简单（简单 bug 也有根因）。
- 正在赶时间（仓促只会保证返工）。
- 管理者要求立即修好（系统化方法比胡乱尝试更快）。

## 四个阶段

进入下一阶段前，必须完成当前阶段。

### 阶段 1：根因调查

**尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告。
   - 其中往往包含准确解决方案。
   - 完整阅读堆栈跟踪。
   - 记录行号、文件路径和错误码。

2. **稳定复现**
   - 能否可靠触发？
   - 准确步骤是什么？
   - 是否每次都会发生？
   - 如果无法复现 → 收集更多数据，不要猜。

3. **检查近期变更**
   - 哪些变更可能导致此问题？
   - 检查 git diff、最近提交。
   - 检查新依赖、配置变化。
   - 检查环境差异。

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名、API → 服务 → 数据库）：**

   **提出修复前，增加诊断检测：**

   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每一层的状态

   运行一次，收集能够表明故障发生位置的证据
   然后分析证据，识别失败组件
   再调查这个具体组件
   ```

   **示例（多层系统）：**

   ```bash
   # 第 1 层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示：**哪一层失败（secrets → workflow ✓，workflow → build ✗）。

5. **追踪数据流**

   **错误位于调用栈深处时：**

   完整的反向追踪方法见本目录的 `root-cause-tracing.md`。

   **快速版本：**
   - 错误值来自哪里？
   - 谁用这个错误值调用了当前代码？
   - 持续向上追踪，直到找到来源。
   - 在来源处修复，不要在症状处修补。

### 阶段 2：模式分析

**修复前先找出模式：**

1. **寻找正常示例**
   - 在同一代码库中定位相似且正常工作的代码。
   - 哪些正常代码与出错代码相似？

2. **与参考实现比较**
   - 实现某种模式时，应**完整**阅读参考实现。
   - 不要略读；逐行阅读。
   - 完全理解模式后再应用。

3. **识别差异**
   - 正常实现和异常实现之间有什么不同？
   - 列出每一项差异，无论多小。
   - 不要假设“那不可能有影响”。

4. **理解依赖**
   - 还需要哪些组件？
   - 需要什么设置、配置和环境？
   - 它作出了哪些假设？

### 阶段 3：假设与测试

**采用科学方法：**

1. **形成单一假设**
   - 清晰陈述：“我认为 X 是根因，因为 Y。”
   - 写下来。
   - 具体，不要含糊。

2. **最小化测试**
   - 作出能够检验假设的**最小**变更。
   - 一次只改变一个变量。
   - 不要同时修复多个事项。

3. **继续前验证**
   - 奏效了吗？是 → 阶段 4。
   - 没奏效？形成**新**假设。
   - 不要在原修改上继续堆叠修复。

4. **不知道时**
   - 说“我不理解 X”。
   - 不要假装知道。
   - 寻求帮助。
   - 继续研究。

### 阶段 4：实现

**修复根因，而不是症状：**

1. **创建失败测试用例**
   - 尽可能简单地复现。
   - 可以时使用自动化测试。
   - 没有框架时使用一次性测试脚本。
   - 修复前**必须**具备。
   - 使用 `superpowers:test-driven-development` Skill 编写正确的失败测试。

2. **实现一项修复**
   - 针对已经识别的根因。
   - 一次只做**一项**变更。
   - 不做“顺手优化”。
   - 不捆绑重构。

3. **验证修复**
   - 测试现在通过吗？
   - 是否破坏其他测试？
   - 问题真的解决了吗？

4. **修复未奏效时**
   - 停止。
   - 计数：已经尝试过几次修复？
   - 少于 3 次：返回阶段 1，根据新信息重新分析。
   - **达到或超过 3 次：停止并质疑架构（见下方第 5 步）。**
   - 未经架构讨论，不要尝试第 4 次修复。

5. **三次以上修复失败时：质疑架构**

   **表明存在架构问题的模式：**

   - 每次修复都在不同位置暴露新的共享状态、耦合或问题。
   - 修复需要“大规模重构”才能实现。
   - 每次修复都会在其他地方制造新症状。

   **停止并质疑基本前提：**

   - 此模式在根本上是否合理？
   - 我们是否只是“因为惯性而坚持”？
   - 应重构架构，还是继续修补症状？

   **尝试更多修复前，与人类协作者讨论。**

   这不是失败的假设，而是错误的架构。

## 红旗——停止并遵循流程

如果发现自己产生以下想法：

- “先快速修一下，之后再调查。”
- “先改 X 看看是否有效。”
- “一次加入多个变更，再运行测试。”
- “跳过测试，我手工验证。”
- “可能是 X，我来修它。”
- “我还没完全理解，但这可能有效。”
- “模式说要用 X，但我会换种方式套用。”
- “以下是主要问题：[未调查就列出修复]。”
- 在追踪数据流前提出解决方案。
- **“再试一次修复”**（已经失败两次以上）。
- **每次修复都在不同位置暴露新问题。**

**以上情况都意味着：停止，返回阶段 1。**

**如果三次以上修复失败：质疑架构（见阶段 4.5）。**

## 人类协作者发出的错误做法信号

**注意这些纠正：**

- “这不是正在发生吗？”——你未经验证就作出了假设。
- “这能让我们看到……吗？”——你本应增加证据收集。
- “别猜了。”——你在没有理解问题时提出修复。
- “深入想想。”——应质疑基本前提，而不只是症状。
- “我们卡住了吗？”（沮丧）——当前方法没有奏效。

**看到这些信号时：停止，返回阶段 1。**

## 常见自我辩解

| 借口 | 事实 |
|---|---|
| “问题很简单，不需要流程。” | 简单问题也有根因；对简单 bug，此流程同样很快。 |
| “情况紧急，没时间走流程。” | 系统化调试比反复猜测更快。 |
| “先试这个，再调查。” | 第一次修复会建立行为模式；应从一开始就做对。 |
| “确认修复有效后再写测试。” | 未经测试的修复无法持久；测试先行可以证明修复。 |
| “同时改多项可以节省时间。” | 这样无法隔离哪项有效，还会制造新 bug。 |
| “参考资料太长，我按自己的理解调整模式。” | 片面理解必然导致 bug；应完整阅读。 |
| “我看出问题了，直接修。” | 看到症状不等于理解根因。 |
| “再试一次修复”（已经失败两次以上） | 三次以上失败意味着架构问题；应质疑模式，不要继续修补。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|---|---|---|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解发生了**什么**以及**为什么** |
| **2. 模式** | 寻找正常示例并比较 | 识别差异 |
| **3. 假设** | 形成理论，最小化测试 | 假设得到确认，或形成新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 已解决，测试通过 |

## 流程表明“没有根因”时

如果系统化调查表明问题确实来自环境、取决于时序或属于外部因素：

1. 说明你已完成此流程。
2. 记录调查过的内容。
3. 实现适当处理（重试、超时、错误消息）。
4. 增加监控/日志，便于未来调查。

**但是：**95% 的“没有根因”其实是调查不完整。

## 辅助技术

以下技术属于系统化调试的一部分，可在本目录中找到：

- **`root-cause-tracing.md`**——沿调用栈向后追踪 bug，找到原始触发原因。
- **`defense-in-depth.md`**——找到根因后，在多层增加验证。
- **`condition-based-waiting.md`**——用条件轮询替代任意超时。

**相关 Skill：**

- **superpowers:test-driven-development**——创建失败测试用例（阶段 4，第 1 步）。
- **superpowers:verification-before-completion**——声称成功前验证修复有效。

## 实际影响

来自调试会话的数据：

- 系统化方法：15–30 分钟修复。
- 随机修复方法：2–3 小时反复尝试。
- 首次修复成功率：95%，而不是 40%。
- 引入新 bug：接近零，而不是经常发生。
