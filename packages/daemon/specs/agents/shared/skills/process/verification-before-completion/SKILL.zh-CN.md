# 完成前验证

## 概述

未经验证就声称工作完成，是不诚实，而不是高效。

**核心原则：**证据永远先于声明。

**此规则为交付服务——它不是凌驾于交付之上的仪式。**它只约束一件事：*声称某项可验证结果成立*（“测试通过”“构建成功”“缺陷已修复”）——先运行检查再作断言，并让检查强度与风险匹配（一行文案调整不需要全套测试仪式）。不要用同义词规避规则；也不要把规则膨胀为对“完成”一词的税负，或以此为由不断重复证明、迟迟不交付可工作的内容。

## 铁律

```
没有新鲜的验证证据，就不能声称完成
```

如果你没有在当前消息中运行验证命令，就不能声称它通过。

## 门禁函数

```
在声称任何状态或表达满意之前：

1. 识别：哪个命令可以证明这项声明？
2. 运行：执行完整命令（新鲜、完整）
3. 阅读：阅读完整输出，检查退出码，统计失败数量
4. 验证：输出是否证实声明？
   - 如果否：用证据说明实际状态
   - 如果是：带着证据说明结论
5. 只有此时：才能作出声明

跳过任何一步 = 撒谎，而非验证
```

## 常见失败

| 声明 | 所需证据 | 不足以证明 |
|-------|----------|------------|
| 测试通过 | 测试命令输出：0 项失败 | 以前的运行、“应该会通过” |
| Linter 干净 | Linter 输出：0 个错误 | 局部检查、外推 |
| 构建成功 | 构建命令：退出码 0 | Linter 通过、日志看起来正常 |
| 缺陷已修复 | 原始症状对应测试：通过 | 代码已修改、假定已修复 |
| 回归测试有效 | 已验证 red-green 循环 | 测试只通过一次 |
| 智能体已完成 | VCS diff 显示变更 | 智能体报告“成功” |
| 需求已满足 | 逐行检查清单 | 测试通过 |

## 危险信号——停止

- 使用“应该”“大概”“似乎”等表述
- 在当前消息中尚未运行检查，就声称某项具体结果已被*证明*（“测试通过”“已经修复”“构建为绿色”）——热情本身没有问题；未经验证的**结果声明**才是危险信号
- 未经验证就准备 commit/push/PR
- 相信智能体的成功报告
- 依赖局部验证
- 认为“只破例这一次”
- 因疲惫而想尽快结束
- **任何暗示成功、却没有执行验证的措辞**

## 防止自我合理化

| 借口 | 事实 |
|------|------|
| “现在应该能工作” | 运行验证 |
| “我很有信心” | 信心 ≠ 证据 |
| “只破例一次” | 没有例外 |
| “Linter 通过了” | Linter ≠ 编译器 |
| “智能体说成功了” | 独立验证 |
| “我累了” | 疲惫 ≠ 借口 |
| “局部检查够了” | 局部结果不能证明整体 |
| “换了说法，规则就不适用” | 精神优先于字面 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] “所有测试通过”
❌ “现在应该会通过” / “看起来正确”
```

**回归测试（TDD Red-Green）：**
```
✅ 编写 → 运行（通过）→ 撤销修复 → 运行（必须失败）→ 恢复修复 → 运行（通过）
❌ “我已经编写回归测试”（未验证 red-green）
```

**构建：**
```
✅ [运行构建] [看到：退出码 0] “构建通过”
❌ “Linter 通过了”（linter 不检查编译）
```

**需求：**
```
✅ 重新阅读计划 → 创建检查清单 → 逐项验证 → 报告缺口或完成
❌ “测试通过，阶段完成”
```

**智能体委派：**
```
✅ 智能体报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
❌ 相信智能体报告
```

## 检查本身撒谎时——内容优先于形态

运行验证是必要条件，但并不充分：检查可能干净退出，却什么也没有证明。以下是绿色检查产生误导的典型方式，也是“证据先于声明”背后的同级失败模式。（更深入的“依据什么验证”说明见 `reference-first-verification`。）

- **断言内容，绝不要只断言形态或数量。**看起来像成功的输出——非零计数、干净退出、没有错误文本——其内容仍可能代表失败。信任检查前，先问失败时输出是什么样：如果失败和成功一眼看去无法区分，检查就没有证明力。（`[1 lines]` 和 `No matches found` 对行数统计而言都可能看起来像“一条匹配”。）
- **将返回值与实际传入值比较——绝不要与对该值的描述比较。**转录中，自信的标签（在未改变原值上方打印 `evidenceRef NOW SET:`）与真正验证难以区分。应将实际结果与实际输入做 diff，而不是与关于输入的声明比较。
- **寻找未经测试的轴。**只对一个轴进行全面覆盖，很容易看起来像整体覆盖。检查所有测试共同依赖什么——健康 manifest、默认选项值、happy path——并把该共同假设视作从未测试的维度。
- **语法检查只证明可解析，除此之外什么都不证明。**干净的 `node --check` / lint / parse 只覆盖语法轴；boot 和 runtime 是未测试轴。可解析 ≠ 正确。
- **失败形态为挂起时，检查不会报告任何信息。**对明确截止时间仅执行裸 `await`，却不重新检查，无法响亮失败。应让它与 timer 竞争，使失败具有可观察形态。
- **通过截断显示读取完整性清单毫无价值。**决定*要修改哪些出现位置*时，应使用 `grep -c` / `grep -o` / 完整行输出统计，绝不要使用 `cut`、`head` 或 pager，因为它们可能隐藏截断位置之后的匹配。区分“我统计到 N 项”（计数）与“我看到 N 项”（显示）。审计多行正文时应**按段落而非按行**——按行过滤既会遗漏长行中的匹配，也会把伴随文字位于下一行的段落误报。随后使用**不同方法**重新审计，不要用构建清单的同一种方法复查，否则会复制同一盲点。（空或很短的输出首先只是对**命令**的声明，必须用第二种方式重新证明。）

## 为什么重要

来自 24 条失败记忆：
- 人类伙伴说“我不相信你”——信任破裂
- 未定义函数被发布——运行时会崩溃
- 遗漏需求被发布——功能不完整
- 在虚假完成 → 重新引导 → 返工上浪费时间
- 违反：“诚实是核心价值。如果撒谎，你会被替换。”

## 何时应用

**以下情况之前始终应用：**
- 任何形式的成功/完成声明
- 任何满意表达
- 任何关于工作状态的正面陈述
- commit、创建 PR、完成任务
- 转到下一项任务
- 委派给智能体

**规则适用于：**
- 精确短语
- 改写和同义表达
- 暗示成功
- 任何表示完成/正确的沟通

## 底线

**验证没有捷径。**

运行命令。阅读输出。然后再作声明。

此规则不可协商。
